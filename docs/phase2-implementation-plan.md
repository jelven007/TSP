## 1. 三步目标与规模口径

| 步骤 | 目标 | 部署边界 | 完成后交付 |
| --- | --- | --- | --- |
| 第一步：单机关键功能迭代 | 完成实时网关、公共行情读模型、短期授权与撤权、容量观测 | 同一台服务器、一个业务 Cell，服务按职责分进程/容器 | 一套功能完整、热路径清晰、可独立发布的单机版本 |
| 第二步：单机百用户迭代 | 支持 100 个独立用户，100 个用户同时活跃在线 | 继续单机、单 Cell；在真实数据规模和后台任务下验收 | 有容量、隔离、持续运行与恢复证据的单机版本 |
| 第三步：DFX 与万人并发 | 完善可靠性、安全性、可观测性、发布恢复及 10,000 人活跃并发 | 根据量测扩展多节点与故障域，按容量需要引入多 Cell | 通过万人业务负载与故障演练的版本，保留向十万人扩展的路径 |

第二步的“100 用户、100 并发”表示 100 个独立账号都同时打开活跃业务页面，订阅行情并执行业务请求；只有 Cookie、空会话或空连接不计为通过。100 个账号都需要代表性私有数据和后台任务，不能用少量有数据账号加大量空账号凑数。

账号数、租户数、活跃用户数、连接数、HTTP RPS、在途请求和后台执行量分别统计。注册默认个人租户继续沿用，但不能将一位用户可以加入多个租户的模型改成账号与租户永久一一对应。

第三步先签收 10,000 人活跃并发；原分析中的 100,000 人、150,000 连接和相应请求预算保留为远期扩展目标。第二步不承担这些远期门槛，第三步的万人验收也不能宣布十万人已经达标。

基础安全与恢复贯穿三步：权限校验、RLS、同源保护、敏感信息保护、计算资源限制和备份不能推迟到第三步。第三步补齐跨节点保障、更强隔离以及规模下的验证。

## 2. 第一步：基于单机版完成关键功能迭代

这一步聚焦上一轮推荐的第一工作包。独立服务仍运行在同一台机器上，先建立职责与协议边界；不把分进程误认为获得了宿主故障高可用。

执行状态：**本地实现、外部 SSE 功能和 100 客户端突发扇出已验证；持续容量、交易时段和发布待签收。**

| 编号 | 工作内容 | 具体结果与验证重点 |
| --- | --- | --- |
| 1.1 | 固定功能与性能基线 | 记录版本、机器配额、活跃业务操作、SQL 次数、API 分位数、网关 CPU/RSS、快照字节与队列年龄；保留同环境前后对照 |
| 1.2 | 独立实时网关与公共行情读模型 | API 与长连接分开资源预算；平台统一采集；按证券/字段聚合订阅；减少 API 副本重复拉取和解码全市场 |
| 1.3 | 短期授权票据与撤权 | Cookie 仍由可信身份服务核验；网关本地验证票据与撤权版本；敏感写实时核验；票据最坏过期与撤权期限 ≤60 秒 |
| 1.4 | 公共行情与私有事件分开恢复 | 行情最新值可合并，有界背压与快照恢复；订单/成交/告警/任务事件保留游标和重同步语义，不能静默覆盖 |
| 1.5 | 前端与现有接口接线 | 优先兼容 SSE；看盘、自选、监控、模拟盘等页面使用批量行情/增量刷新；退出、切租户和权限变化清理旧私有缓存与订阅 |
| 1.6 | 建立可定位问题的运行状态 | 分开进程存活、请求就绪、行情新鲜度与功能状态；研究/通知异常不应让可用看盘请求全部摘流 |

单机私有事件可采用专用数据库通知监听与持久事件补扫，或等效的受控本机分发；唤醒丢失仍能从 SQL 追赶。避免按全部租户高频轮询。若使用 LISTEN，保留专用 direct/session 连接，不能放入 PgBouncer 事务池。

单机撤权也必须覆盖全部 API/网关进程：进程内字典不能作为唯一撤权来源，失去广播后由硬 TTL 收敛；续期重新核验权威状态。授权有效时点沿用架构分析的敏感写/撤权约束。

账户增量投影与研究到期调度可以并行设计，但不作为实时网关首次交付的前置；它们列入第二步必须完成的工作，避免第一步扩展成全部二期工程。

第一步完成条件：

- 同环境保留一期 100 人活跃业务回归；角色功能、私有隔离与行情业务口径通过，不能只验证网关可连接。
- 无私有事件时，SQL 工作不再随所有订阅租户产生固定高频空查询；网关稳定期不再逐连接每秒读取身份库。提交前后量测证据。
- 断线、慢消费者、重复事件、缺口、权限撤销与广播中断均有明确恢复结果；私有数据不跨租户。
- 基本看盘、研究、通知等状态分别报告，已有数据的新鲜度真实展示。
- 发布和回退步骤形成可执行记录；涉及新 schema 时保持扩展/收缩兼容，回退保留上线后业务增量。

交付：功能变更说明、协议/授权契约、针对性回归结果、前后基准及单机发布说明。性能收益以量测为准，不因拆出服务就宣称提高了容量。

### 3.1 验收负载

在固定的一台服务器上保留 100 个用户身份与代表性数据，按 10 →50 →100 个活跃用户渐增，再保持百人稳态并注入重连和查询突发。全部账号参与，不保留只注册不操作的空样本。

前台基线建议沿用每用户平均 20 只证券、每秒 1 批，并单独覆盖高订阅、多标签页及慢连接。业务请求比例、规则量、台账长短分布和研究任务复杂度在压测前固定，报告同时列出各项实际执行量。

100 用户每五秒一次 HTTP 请求相当于 20 RPS，仅是初始负载换算；上线容量不能只凭这个数字判定。登录/重连、首次快照、集中查询和后台执行另测，拒绝与排队分别计量。

采用真实协议和独立身份；可用脱敏样本及行情回放复现压力，同时补充真实交易日链路验证，分别标明回放和源端延迟。不得生成邮件/通知洪峰影响真实第三方收件人，使用隔离测试渠道。

| 类别 | 阶段门槛 |

## 4. 第三步：完善 DFX，验收万人活跃并发

第三步按依赖分成几个工作包，仍属于二期第三步，不增加新的产品期次。先让同一 Cell 在多节点故障时安全工作，再按容量拆 Cell。

| 编号 | 工作包 | 具体完成内容 |
| --- | --- | --- |
| 3.1 | 可观测性与上线治理 | 请求/任务/行情版本关联；服务/Cell/类别指标；权限审计；队列年龄与数据新鲜度告警；灰度、停止推广、排空回退和 schema 兼容 |
| 3.2 | 多节点可靠性 | API、网关、身份和 Worker 跨节点；实例级健康聚合；数据库连接/选主与旧主隔离；公共采集主备租约和发布 fencing |
| 3.3 | 安全与强隔离 | 管理员 MFA、集中限流与撤权、内部服务身份、密钥轮换、私有对象短期授权；gVisor/microVM 等强沙箱的功能与性能验证 |
| 3.4 | 跨节点状态与任务 | SQL 为事实源，Outbox/JetStream 分发与唤醒；持久配额、attempt/epoch/租约与旧结果拒绝；对象 manifest/CAS 发布及输入版本保留 |
| 3.5 | 按容量引入多 Cell | 可信租户目录与路由、领域锁和 RLS；源 fencing→目录 CAS→目标启用的持久迁移状态机，任一故障点保持单写 |
| 3.6 | 万人并发与恢复验收 | 独立用户混合负载、重连/登录与查询洪峰、后台任务及故障同时覆盖；量测剩余容量、成本和区域恢复能力 |

单 Cell 的安全容量和最大故障域退出后的余量决定 Cell 数量，多节点不要求机械对应多个 Cell。消息、对象存储、数据库与密钥服务也需独立故障范围；增加容器副本不等于增加故障域。

万人压力按 100 →1,000 →3,000 →10,000 个活跃用户形成曲线；先在较小负载验证撤权、任务重复、迁移和旧主隔离，再观察这些行为在万人压力下是否仍满足指标。

### 4.1 容量与 DFX 门槛

| 类别 | 当前第三步验收安排 |
| --- | --- |
| 活跃用户 | 10,000 个独立用户同时操作完整产品；验证 15,000 连接余量作为初始建议，多标签页按实测修订 |
| HTTP 与突发 | 按远期相同人均请求预算，初始建议 2,000 RPS 稳态、5,000 RPS 突发；10,000 同时轻查询有界排队，建议全部 ≤30 秒 |
| 时延与持续运行 | 轻 API P95 ≤300ms、P99 ≤1s；有效请求 5xx/超时 <0.1%；完整交易日和 72 小时负载 |
| 撤权与安全 | 常规连接最坏撤权 ≤60 秒，广播中断不能无限续期；敏感写的授权有效时点明确；私有数据、凭据和计算资源隔离通过 |
| 可靠性 | 沿用核心业务月可用性 99.95%、节点/AZ RTO ≤5 分钟的设计目标；通过实例/数据库/消息/网络故障演练，验证降级行为 |
| 关键账本 | RPO=0 以同步副本落盘确认、提升水位与旧主 fencing 为条件；失去同步确认时拒绝/等待或明确降低承诺，不能静默转异步 |
| 灾备 | 区域 RPO ≤5 分钟、RTO ≤60 分钟保留为目标；身份目录、账本、任务、对象版本与密钥联合恢复，未演练不宣布达标 |
| 成本与扩展 | 按实际连接、出口、数据库/复制、计算、对象、日志及 AI/通知计量；形成单 Cell 安全容量与扩展余量证据 |

2,000/5,000 RPS 和 15,000 连接是依据原远期预算比例得到的初始验收建议，不是实测结果或采购配置。压测前固定请求比例、突发持续时间、后台配额与资源配置；不足时修复瓶颈再复测。

故障场景至少覆盖：网关节点退出与分批重连、数据库主库退出、身份/撤权广播中断、消息重复/不可用、采集旧主恢复、计算租约过期、对象冷读失败、迁移各状态中断及最大规划故障域退出。

交付：万人容量报告、故障与恢复报告、安全验证、成本曲线、发布/回退 runbook 和扩展建议。最终结果分别标明已通过、未通过和未执行，不能用一次健康探测替代 DFX 签收。

## 5. 提交与发布节奏

每个工作编号尽量对应一个可独立评审的变更，跨端契约改动在同一工作包联调。先完成本地定向验证与提交，再按会话授权推送和发布；本计划本身不表示已经实施或已经部署。

第一步和第二步的本地工作已形成证据，但对应候选环境与持续运行门槛仍需分别签收；这些门槛完成后再进入第三步规模扩展。贯穿各步的安全、观测和领域正确性可以提前完成，不必等待最后阶段。

每次发布带版本、功能回归、容量/资源结果、迁移影响与增量保留方案。故障后的回退保护新写，租户迁移保持单写，金融数据契约沿用 [贡献指南](../CONTRIBUTING.md)；未知成本与机器数量通过量测收敛。
