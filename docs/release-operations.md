# TSP 发布与服务运营手册

统一版本候选、产物发布、上线观察、服务开通、公告、用户支持与反馈。当前通过已有页面、日志和人工记录执行，不声明新增运营后台、自动公告或收费系统。生产状态以[版本基线](version-baseline.md)为准，技术操作见[运维手册](operations.md)，验收口径见[测试手册](testing.md#acceptance)。

新安装的数据同步默认开启，首次同步在后台执行，管理员从数据总览查看阶段与失败原因。
开通验收应确认各任务开关、源能力和执行窗口；已保存关闭值保持关闭，支持人员先核对实际
配置再指导重试。秒级归档默认开启且保留期 0，观察磁盘与队列；财务周期同步检查最后同步
时间和发布版本。完整参数见[初始化默认值](operations.md#config-数据页初始化默认值)。
这次默认值调整不代表既有生产服务已升级或已通过真实交易时段验收。

<a id="1-发布原则"></a>
## 1. 发布原则

- 发布以可追溯的 Git 提交、版本号、产物和验证记录为单位。
- 代码通过 CI、产物构建成功和生产可用是三个不同结论，必须分别确认。
- 生产部署固定版本 tag、提交 SHA 或镜像 digest，不依赖可变的 `latest`。
- 配置、数据迁移和代码升级分别评估，先备份再写入。
- 当前不具备自动灰度和自动业务回滚；发布负责人必须保留人工停止条件。
- 发布说明只陈述已验证能力，不把设计目标或单次外部网络成功写成保证。

<a id="2-发布产物"></a>
## 2. 发布产物

| 产物 | 自动化 | 触发 | 说明 |
| --- | --- | --- | --- |
| CI 结果 | `.github/workflows/ci.yml` | push/PR 到 `main` | 后端全量测试；前端 test、lint、build |
| Git 版本标签 | CI 的 Tag Job | 主线版本和前后端质量门成功 | 自动创建 `v<应用版本>`，固定到实际通过测试的 SHA |
| 容器镜像 | `.github/workflows/docker.yml` | `main` CI 成功、`v*` tag、手动 | 发布到当前仓库配置的 GHCR；使用前必须核验可见性与 digest |
| 桌面安装包 | `.github/workflows/release.yml` | 手动且质量门通过 | Windows x64、macOS ARM64、Linux x64 |
| GitHub Release | 桌面发布 workflow | 手动 | 所选平台全部成功后发布并冻结；草稿可补齐 |
| 更新清单 | `latest.json` | 桌面产物后 | 仅列实际存在资产及 SHA-256 |
| 构建与运行文件清单 | `build-manifest.json` / 安装包 `.manifest.json` | 构建及安装包封装 | 源码 SHA、工作区状态、文件哈希及安装包哈希，见[离线升级备份](reference/engineering.md#build) |
| MCP 包 | `mcp-server/` | 独立维护 | 版本不必与主应用完全同步 |

`main` 的 CI 先写回自动版本提交，前后端质量门均检查该提交；Docker 读取该次
成功 CI 的 `ci-revision` artifact，构建相同提交并写入提交 SHA 和应用版本镜像标签。
`latest` 单独串行提升，只接受提升时仍为当前 main 的构建 SHA；手动和旧 tag
构建不更新它。CI 事件的原始 `head_sha` 不能代替实际通过质量门的 SHA。
`v*` tag 和手动触发会在 Docker workflow 内重新执行后端、前端质量门，通过后
才构建镜像。Dockerfile 的 pnpm 与 uv 安装使用锁文件冻结模式，不允许锁文件
不一致时退回非冻结解析；Codex CLI 使用固定版本构建参数。

桌面 workflow 同样先执行后端全量测试和前端 test、lint、build，再启动所选平台
的打包矩阵。手动触发不再构成绕过质量门的路径。
打包嵌入源码清单，生成包外运行文件清单；上传前再次核验运行文件，拒绝源码
dirty、提交不符或包后文件变化。运行清单不修改已签名的 macOS `.app`。
Docker 清单包括 app/static、锁文件和原生 wheel；Compute 先验证基础镜像清单，
再对当前源码生成清单。旧镜像没有清单时应先重新构建 API 基础镜像。

<a id="3-版本规则"></a>
## 3. 版本与渠道

应用格式、进位、远程main自动分配、重跑与标签规则只在[CONTRIBUTING 第10.1节](../CONTRIBUTING.md#101-主线版本规则)定义。本地和功能分支不加号。质量门、镜像与桌面产物固定同一提交，源码标签、安装包发布和生产切流分别留证据。多人协作与远程权限见[工程参考](reference/engineering.md#collaboration)。

<a id="31-版本保留"></a>
### 3.1 版本保留

日常支持集合保留最新版本和最近五个历史版本，共六个源码恢复点，用于升级与回滚验证。
每次新版本标签通过质量门后，按主应用语义版本排序重新确认集合，并清理更早版本关联的可变
资源：

- 已归并的远程功能分支；
- 已废弃且未冻结的 Draft Release；
- 不再作为回滚入口的本地构建缓存和临时验收目录。

`v*` 源码标签受不可更新、不可删除规则保护，是不可变审计点；不能为了把远程标签
数量压缩到六个而绕过规则、强制删除或移动标签。已发布的 immutable Release 同样
不能覆盖或追加资产。这里的“最新加五个历史版本”表示活跃支持和回滚集合，不表示重写
Git 历史；生产仍以固定镜像 digest 和备份为准。

历史版本缺少现存 `v*` 标签时，以 Git 中的版本提交核对 `VERSION` 和包元数据，
建立 `recovery/v<版本>` 恢复标签；它不代表重新通过 CI 或已发布安装包。
2026-10-24清单仅为当时快照，见[历史版本恢复点](../reports/production-integration-20261024/version-retention.json)。
每次合并后获取新标签，再用[源码恢复工具](../scripts/release/source_recovery.py)生成新的六版本集合：

```bash
git fetch origin main --tags
python3 scripts/release/source_recovery.py create --revision origin/main \
  --output deliverables/version-recovery-new
python3 scripts/release/source_recovery.py verify --output deliverables/version-recovery-new
```

输出目录必须尚不存在。工具核对主线提交和同版本标签，按版本选择五个已合入的历史版本，
生成六份源码归档、提交/SHA-256清单，并在完整校验后发布目录；不会覆盖旧集合或改动任何标签。
确认新集合后，将其作为活跃恢复集合，按清单退役旧本地重复归档。
源码包不包含运行数据、秘密配置、已安装依赖和生产镜像，恢复生产仍须使用匹配备份与产物。
清单和哈希用于完整性复核，不是数字签名或新的生产放行证据。

2026-10-25候选继承初始化后默认自动同步，纳入官方目录、管理员默认个人空间、统一顶栏
与数据总览。对用户说明：目录每天09:00及启动时更新，旧自定义时间不再生效，
行情自动同步关闭不暂停官方目录；管理员手工目录修改可能被后续官方同步重新核对。
新部署仍须具备非Windows完整多租户基础服务；注册/找回和邮件通知需要配置SMTP。
逐组文档与实际验证见[最新整合记录](../reports/production-baseline-20261025/verification.md)。

<a id="4-角色与职责"></a>
## 4. 角色与职责

小型项目可以由同一人承担多个角色，但检查项不能省略：

| 角色 | 责任 |
| --- | --- |
| 版本负责人 | 确定范围、版本号、冻结点和最终放行 |
| 开发负责人 | 说明实现、兼容、数据和回滚影响 |
| 测试负责人 | 执行自动化与人工验收，记录未覆盖风险 |
| 运维负责人 | 备份、部署、健康检查、观察和回滚 |
| 运营负责人 | 发布公告、反馈归类、指标回顾和后续决策 |

<a id="5-发布输入"></a>
## 5. 发布输入

进入版本候选前必须具备：

- 需求或问题说明，以及对应验收条件。
- 聚焦的代码和文档变更。
- 配置、schema、数据口径和 API 兼容性结论。
- 实际执行的测试结果。
- 风险、降级和回滚方案。
- 用户可见变化的截图或操作说明。
- 已知限制和未完成项。

缺少关键信息时可以发布预发布版本，但不能标记为稳定版本。

<a id="6-发布前检查"></a>
## 6. 发布前检查

<a id="61-代码和文档"></a>
### 6.1 代码和文档

- [ ] 目标提交已复审，没有未解决的 `P0`、`P1`、`P2`。
- [ ] 版本号位置一致。
- [ ] `README.md`、需求中的当前功能及`操作说明书.md`与界面一致。
- [ ] 需求、架构、测试、运维和专项方案已同步受影响内容。
- [ ] 配置示例不含真实密钥，新增配置有默认值和升级说明。
- [ ] OpenAPI、Provider、Parquet 或 JSON 契约变化有兼容结论。
- [ ] 变更日志区分新增、修复、行为变化、已知限制和迁移要求。

<a id="62-验证"></a>
### 6.2 验证

- [ ] 同一提交的 CI 后端和前端 Job 通过。
- [ ] 适用的 Ruff、定向测试和性能/并发测试通过。
- [ ] 真实 Provider 声明有对应日期的脱敏烟测记录。
- [ ] Docker 或目标桌面平台完成启动和核心流程烟测。
- [ ] 升级副本完成旧数据读取或迁移验证。
- [ ] 备份和回滚步骤在兼容版本上演练。
- [ ] `git diff --check`、文档链接和代码围栏检查通过。
- [ ] 构建清单的提交、版本、文件哈希与目标产物相符；二开差异备份已核验完整。

<a id="63-安全和合规"></a>
### 6.3 安全和合规

- [ ] Git 历史、产物、日志和截图不含密钥、Token、Webhook 或用户数据。
- [ ] 默认配置不把无密码服务暴露到公网。
- [ ] API Token 使用最小 scope。
- [ ] 第三方数据源和依赖的许可、条款与风险说明保持准确。
- [ ] 发布说明包含研究用途和非投资建议声明。

<a id="7-docker-发布流程"></a>
## 7. Docker 发布流程

<a id="71-版本候选"></a>
### 7.1 版本候选

1. 合并目标变更，等待 CI 自动写回版本提交，并从 CI 摘要记录候选提交 SHA。
2. 等待该次 CI 对版本提交的质量门全部通过。
3. 检查由该次 CI 成功事件触发的 Docker workflow、SHA 标签和多架构 manifest。
4. 在隔离环境使用 SHA 标签启动，不使用本地未提交代码。
5. 执行健康、登录、持久化、数据和核心研究烟测。

示例：

```bash
export IMAGE_REF='ghcr.io/jelven007/tsp'
docker pull "${IMAGE_REF}:<commit-sha>"
docker image inspect "${IMAGE_REF}:<commit-sha>"
```

镜像名称、可见性和实际 SHA 标签格式以当前仓库 workflow 产物为准。未核验成功前，
部署文档和发布说明不得把该镜像写成可用入口。

<a id="72-稳定版本"></a>
### 7.2 稳定版本

1. 完成发布前检查并冻结已通过主线 CI 的版本提交。
2. 核对 CI 自动创建的 `v*` Git 标签指向该提交。
3. 确认该次 CI 触发的 Docker workflow 和版本镜像标签均成功。
4. 使用版本 tag 在验收环境复测。
5. 发布变更说明和升级/回滚指引。
6. 生产环境按维护窗口备份并部署固定版本。

不要因为 `latest` 已更新而跳过版本 tag 验收。`main` 上任何提交都可能刷新
`latest`。

<a id="8-桌面客户端发布"></a>
## 8. 桌面客户端发布

桌面发布通过 GitHub Actions 手动触发：

```bash
gh workflow run release.yml \
  -f version=v0.4.1 \
  -f platforms=windows \
  -f prerelease=false
```

`platforms` 支持逗号分隔的 `windows,macos,linux`。当前 macOS 只构建 Apple
Silicon。workflow 会：

1. 校验输入为已有 main 标签，解析完整 SHA，并校验该源码中的版本一致。
2. 在 Ubuntu 质量门中执行后端 frozen 安装和全量 pytest。
3. 在同一质量门中执行前端 frozen 安装、Vitest、ESLint 和生产构建。
4. 质量门通过后构建前端和各平台后端运行环境。
5. 使用 PyInstaller 构建应用。
6. Windows runner 验证 x64/Windows 10+ 目标约束，运行便携版 EXE 自检。
7. Windows 安装包执行静默安装、启动自检、静默卸载和用户数据保留验证。
8. 生成所选平台安装包并上传 Draft Release。
9. 汇总 Draft Release 上的目标资产，生成带 SHA-256 的 `latest.json`。
10. 所选平台全部通过且资产齐备后发布 Release；immutable 规则从此刻冻结资产。

失败时保留草稿，重跑补齐后再发布；已发布的冻结版本不能追加平台资产。
单个平台成功不代表所有平台已发布。每次发布后检查：

- Release tag、标题、预发布标记和说明。
- 文件名中的版本号。
- 目标平台资产是否真实存在。
- `latest.json` 是否只列存在的资产。
- 每项 URL、大小和 SHA-256。
- 新安装、覆盖升级、启动和检查更新流程。

<a id="9-部署上线"></a>
## 9. 部署上线

<a id="91-上线顺序"></a>
### 9.1 上线顺序

1. 宣布维护窗口和影响范围。
2. 记录当前版本、配置摘要和镜像 digest。
3. 停止写入并执行完整备份。
4. 部署固定版本；独立模式单主写，完整多租户按Platform/API/Gateway/四类Worker与依赖启动，不增加共享目录写副本。
5. 查看启动日志并执行 `GET /health/live` 与 `GET /health/ready`。
6. 登录并执行能力矩阵、数据、策略、回测、监控、模拟交易和开放接口烟测。
7. 恢复定时任务和外部流量。
8. 进入观察期，保留上一版本和备份。

<a id="92-手工渐进验证"></a>
### 9.2 手工渐进验证

当前没有自动灰度。风险较高的版本可以在独立数据副本上执行：

1. 空目录启动，验证初始化。
2. 脱敏旧数据副本启动，验证兼容。
3. 小范围日期或少量标的同步，验证数据口径。
4. 全量同步或重建。
5. 生产实例维护窗口切换。

不得让候选实例和生产实例同时写同一数据目录。

<a id="93-停止条件"></a>
### 9.3 停止条件

出现以下任一情况立即停止推广并评估回滚：

- 健康检查失败或启动循环。
- 数据目录不可写、异常缩小或出现 schema 损坏。
- 能力路由与配置不符，或发生未声明的跨源回退。
- 选股、回测、监控或模拟交易出现错误金融口径。
- 身份认证或 Token scope 失效。
- 任务持续失败、内存异常增长或磁盘快速耗尽。

<a id="10-发布后观察"></a>
## 10. 发布后观察

观察窗口由变更风险决定，至少覆盖受影响功能的一个完整业务周期。盘中和盘后功能
应分别观察对应交易时段。

关注项：

- HTTP 健康、进程重启次数和错误日志。
- Provider 成功率、超时、限流和数据最新时间。
- 09:25 竞价发布与 15:35 盘后任务终态。
- 同步、回测、挖掘和复盘任务的排队、取消和失败。
- SSE 重连、页面错误、监控触发和通知失败。
- 磁盘、内存、CPU 和数据增长。
- 用户反馈中的版本、数据源、日期和复现条件。

当前仓库提供受会话保护的 `/api/observability` 进程内 HTTP 快照，但没有集中
遥测、长期指标留存或运营分析平台。上述指标仍需结合应用页面、日志和部署环境
采集，不能虚构“无反馈即无问题”。

<a id="11-回滚"></a>
## 11. 回滚

发布前必须明确采用哪一种回滚：

| 场景 | 回滚方式 |
| --- | --- |
| 代码错误，未写不兼容数据 | 切回上一固定镜像或提交 |
| 配置错误 | 恢复已审计配置并重启 |
| 新版本写入不兼容数据 | 排空/停写，保存当前数据与增量水位；隔离验证前向修复或携带增量恢复，切匹配代码并对账 |
| 外部 Provider 故障 | 停止相关任务或明确禁用能力，保留上一份有效数据 |
| 单个平台桌面包故障 | 标记受影响渠道并停止推广；冻结Release资产保持不可覆盖，新版本修复后重新验收 |

不能默认恢复旧快照丢弃新注册、成交/权益/退出意图或研究任务；Cell回退携带增量且epoch递增。

回滚不以“旧进程已启动”为完成标准。还要验证版本、数据范围、策略、监控、模拟
账户和开放接口，并记录回滚期间的数据缺口。

<a id="service-5-支持事件与反馈关闭"></a>
## 13. 反馈、事件与用户支持

1. 收集版本/模式、时间、标的/任务/请求ID、预期与实际、最小复现和脱敏证据。
2. 按[测试缺陷分级](testing.md#11-缺陷严重级别与放行)判断P0–P3。
3. 数据错误/越权/账本错误立即隔离受影响能力，停止新增写入或推广，保留现场。
4. 运营说明用户影响，开发定位调用链，测试建立失败样本，运维验证恢复或处置。
5. 修复后核对同版本回归、产物/配置、增量与对账，在已授权流程内发布。
6. 用户能执行升级/恢复且证据确认后关闭，回写需求、方案、测试或Runbook。

通知测试消息和真实触发分开；长压测使用隔离渠道，不能向真实收件人外发洪峰。
对未取得终态的调查保留“待补证”，不把最后记录的PID/心跳当作当前在运行。

<a id="14-运营复盘"></a>
## 14. 运营复盘

每个稳定版本或重大事故后记录：

- 计划范围与实际范围是否一致。
- 缺陷来自需求、设计、实现、测试、发布还是运维。
- 哪个门禁本应更早发现问题。
- Provider 和真实数据验证是否具有代表性。
- 安装、升级、回滚和恢复耗时。
- 文档是否让非开发人员可以独立完成操作。
- 后续行动、负责人和目标版本。

复盘结论应更新需求、架构、测试或 Runbook，而不是只保留在聊天记录中。

<a id="15-当前流程缺口"></a>
## 15. 当前流程缺口

以下能力尚未自动化，发布时需人工控制：

- 没有自动化 Web 端到端和视觉回归门禁。
- 没有真实 Provider 的稳定发布环境。
- Windows 已有原生 runner 安装/启动/卸载烟测，但没有 GUI 自动化、覆盖升级及
  Windows 10/11 消费版真机矩阵；macOS/Linux 桌面安装仍需人工验证。
- 没有自动备份、恢复验证、灰度和业务回滚。
- 没有集中监控、告警、错误聚合和运营指标。
- 没有自动生成完整 changelog 与需求追踪矩阵。

这些缺口是风险声明，不代表当前版本已承诺实现。后续若补齐，应同时更新 workflow、
测试指南、运维手册和本文。

<a id="service-2-开通与用户生命周期"></a>
## 17. 开通与用户生命周期

| 模式 / 任务 | 当前操作与完成检查 |
| --- | --- |
| 完整多租户开通 | 管理员按部署规范初始化，默认获得个人租户空间与业务能力；已有租户选择保留。用户经口令/邮箱验证注册，个人空间就绪后进入行情；失败重试不重复建空间 |
| 角色/状态管理 | 当前管理员/租户两角色；最后有效管理员不可停用/降级，变更撤销受影响授权，直接API仍校验 |
| 独立服务 | 邮箱认证但业务空间共享，告知数据可见边界 |
| Windows个人空间 | 本地管理员首次进入后改密；暂停注册/找回/租户切换，损坏身份从匹配备份恢复 |
| 外部工具 | 当前scope和Token管理，明文仅创建时；吊销后重建凭据，MCP不提供模拟交易下单 |
| 数据/AI/通知准备 | 有权管理员配置依赖；向导完成、保存设置、同步成功和通道可投递分别检查 |

引导用户先建立自选/分组，再查看详情、配置定义、运行短研究与前向观察。
首次看盘不要求普通用户配置全市场采集。注册与模拟账户是不同对象，不涉及真实资金。

当前没有通用销户/回收站/自动撤销保证。删除需求先确认对象、权限、活动引用、
数据许可和备份策略，再走已有受控操作或维护流程；不能用清库代替注销或证据归档。

<a id="service-3-公告与变更沟通"></a>
## 18. 公告与变更沟通

每次公告列：适用版本/完整提交或产物、部署渠道、用户可见变化、影响范围、
维护窗口/状态、配置/数据兼容、操作步骤、已知限制、恢复与反馈入口。
源码通过、安装包发布和生产切流分别公告，未更新生产不称“已上线”。

目录调整告知维护者新脚本模块路径和CI入口；用户页面按现有操作说明。
告警/暂停公告区分数据陈旧、研究不可用、渠道投递失败与账务阻断，保留上次有效值。
公告使用已有渠道，由有权负责人发布；本次文档更新不自动发送消息。

<a id="service-4-日常质量与成本观察"></a>
## 19. 日常质量与成本观察

| 业务结果 | 现有证据 / 目标扩展 |
| --- | --- |
| 可进入、可看盘 | 登录/权限、页面错误、请求ID、有效日期与覆盖；跨实例聚合为目标 |
