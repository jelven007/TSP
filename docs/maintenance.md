# 文档维护与历史资料清理

核对日期：2026-11-01。本文定义文档工程的归属和清理方法；
产品功能、权限、数据保留和版本规则仍以对应主手册为准。

本次临时资料清理保留正式Markdown报告、必要截图及统一Excel；
一次性代码、重复原文／压缩日志、旧研究导出包和原始行情明细不进入发布源码。
删除前核对引用、附件哈希和受控归档；历史证据链接缺失须修正为仍保存的报告，
不能虚构原日志仍在。范围及结果见[整合记录](../reports/release-consolidation-20261101.md)。

## 1. 唯一归属

| 内容 | 权威位置 | 更新责任 |
| --- | --- | --- |
| 项目定位、环境和入口 | 根 README、开始使用 | 项目维护者、启动或模式变更作者 |
| 日常操作与页面行为 | 操作说明书 | 功能作者 |
| 需求 ID、状态与验收条件 | requirements.md | 需求维护者、功能作者 |
| 架构、拓扑和数据血缘 | architecture.md | 架构与模块维护者 |
| 数据口径、代码和复审规范 | CONTRIBUTING.md | 工程维护者 |
| 协议、字段与真实扩展点 | reference、api.md、secondary-development.md | 接口或领域维护者 |
| 测试方法与签收模板 | testing.md | 质量维护者 |
| 发布产物、支持与运营 | release-operations.md | 发布负责人 |
| 安装、配置、备份和故障处理 | operations.md、deploy | 运维维护者 |
| 源码/发布/运行版本状态 | version-baseline.md | 发布或环境切换作者 |
| 历史证据与未完成调查 | reports | 记录作者 |

变更发生时立即更新受影响内容，至少每月复核一次。
正文描述现行规则；旧部署日志、测试计数、临时路径和一次性采集结果不反复粘贴到手册首页。
引用已有证据时说明原版本、环境和窗口，新增验证只记录实际执行的结果。

## 2. 修改与迁移

1. 完整阅读 AGENTS、CONTRIBUTING；核对工作区已有修改及真实调用链。
2. 确认现行功能、历史记录和目标设计的区别。
3. 将规则归入唯一主章节，同步导航、源码注释中的入口和相邻文档链接。
4. 保留全部需求 ID、八模块范围、状态列和独有金融/安全/兼容约束。
5. 保留已公开章节锚点，或同步全部调用方；不保留误导性的旧状态。
6. 核对字段、命令、路径和运行模式，执行适用检查。

后续设计须明确标记“目标”或“按需扩展”。找不到源码定义和契约测试的接口，
不能按已实现功能描述。

## 3. 清理范围

可以清理的对象必须有具体依据，例如：

- 已被现行手册承接且没有有效引用的重复说明和过程回执。
- 已有完整文件后的重复下载分片、解压镜像层等可重建缓存。
- 外部仓库的临时全文副本、失效导航和不再用于当前分析的复制文件。
- 本次或已结束任务留下的调试输出，以及 `.DS_Store` 等系统元数据。

不能仅凭日期、体积或目录名判定为垃圾。
检查静态引用、运行时加载、验收依赖、构建清单和仍未完成的调查。
当前发布原始证据、未提交工作、用户保留策略及结果、所需恢复点应保留。

业务数据清理另走对应授权和备份流程。文档整理不删除
`data/`、数据库、行情分区、身份、SMTP 配置、用户策略或生产备份，
也不把任务缺口清单当作无用文件。

## 4. 证据目录

`reports/` 保存可追溯的源码、环境、窗口、命令、结果和限制；
`deliverables/` 保存用户需要的离线交付或策略成果。
源码恢复点使用专用工具与清单管理，不靠散落的报告目录代替。
中间脚本、下载缓存和临时截图使用工作区外的任务目录。

文件删除或移动前确认是否已经修改、是否有后续任务依赖。
仍需引用的历史结论保留原文；清理被替代副本时更新引用，并记录准确范围。
不通过修改历史测试计数或删除失败证据制造“全部通过”。
持仓整批删除须同步需求、操作、架构、内部API、测试及运维章节；
维护时保留每日编号累计、租户隔离、失败回滚和历史股票逐只删除契约。
文档整理不得据此删除任何实际批次或派生提醒。

## 5. 本地检查

从仓库根执行：

```bash
make check
python3 scripts/check_docs.py --include-reports
make test-tooling
```

`make check` 核对工程目录、Markdown 链接/锚点/围栏、八模块需求、
保留编号、版本一致性和 diff 空白。
历史引用检查包含报告目录。文档契约回归会验证损坏路径、缺失模块、
重复 ID 和缺失状态能被拒绝。

项目目录移动或改名后，旧虚拟环境的可执行脚本可能仍引用原绝对路径。
若`make test-tooling`无法启动pytest，可用同一项目解释器执行：

```bash
uv run --project backend --frozen --no-sync python -m pytest tests/tooling -q
```

新开发环境按[开始使用](getting-started.md)用冻结锁准备依赖；
运行环境的目录或依赖修复先按原部署流程处理。

文档检查不能证明真实行情完整、接口业务正确、全部测试通过或生产仍然健康。
本次修改说明应只报告实际检查范围。
