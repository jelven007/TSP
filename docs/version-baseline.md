## 2. 版本标识规则

主应用版本统一采用 `a.b.cd`：`a=0..9`、`b=0..9`、`cd=0..99`，末段不补零，
规则起始值为 `0.4.0`，当前值见上表。本地迭代、提交、本地合并和功能分支推送
不更新版本；变更推送到远程并集成到 `main` 后，由 CI 自动从 `cd` 加一，
包括功能、修复、文档和构建配置；一次远程主线 push（合并或批量推送）计一次更新。
PR 只检查版本格式和事实源一致性，不要求提前加号。自动提交同步当前版本文件、
锁文件和适用文档，按来源 SHA 去重，工作流重跑不会重复递增。
`cd=99` 后 `b` 加一并将 `cd` 归零；
`b=9` 且 `cd=99` 后 `a` 加一，并将 `b`、`cd` 归零。完整规则和校验脚本见
[`CONTRIBUTING.md`](../CONTRIBUTING.md)及[`scripts/versioning.py`](../scripts/versioning.py)。

一次可复现交付必须同时记录：

1. 应用语义版本，以交付提交中的 `VERSION` 为准。
2. 完整 Git commit SHA。
3. 部署环境和 schema 版本。
4. 镜像 digest 或桌面产物 SHA-256。
5. 对应测试、发布和恢复证据。

历史上的 `0.3.11` 标签、后续定制源码和生产提交曾存在同号不同提交。自动分配应用
版本后，前后端质量门通过的主线提交会自动创建同版本 Git 标签；桌面稳定 Release
和生产状态仍独立验收，任何部署、缺陷或验收记录仍必须以
commit SHA 为主标识。CI 质量门和后续镜像使用自动版本提交的同一个 SHA，
可从该次 CI 的摘要及 `ci-revision` artifact 核对。

`06d4e0b` 和 `b360d77` 的功能修复更新曾未同步递增应用版本，仍写作 `0.4.0`。
随后以 `0.4.1` 补齐版本，并取消校验脚本和开发规则中的“版本不变”例外；
此为当时的手动递增策略。现调整为远程主线集成后自动递增，本地与 PR 可以保持
版本不变；既有提交及报告不追溯改写。

## 3. 分支与发布归类

- `main`：唯一集成主线，必须包含已经决定保留的最新代码和文档。
- 功能分支：只承载尚未归并的工作；归并后不再作为“最新版”引用。
- `v*` Git 标签：主线 CI 质量门通过后自动创建的不可变源码版本点；同名冲突不覆盖。
- 稳定 Release：对应标签的目标产物完成验收后发布，不由自动源码标签推断。
- 生产版本：以实际部署提交和镜像 digest 为准，不自动等同 `main` 或最新标签。
- 历史报告：记录当时事实，不追溯改写成当前状态；文档顶部的当前状态应链接本文。

多人协作的分支基线、主线并发、回滚、镜像指针和远程权限见
[多人协作与版本管理](reference/engineering.md#collaboration)。远程已启用 main 禁止删除和
非快进、`v*` 标签禁止更新和删除；个人仓库拒绝内置 Actions App bypass，
完整 PR/复审/质量强制规则仍需专用 GitHub App，不能从模板存在推断已启用。

## 5. 更新要求

应用版本字段由远程主线 CI 自动同步；其余以下状态变化仍须更新本文件并同步
受影响文档：

- `main` 归并新的版本候选；
- 应用语义版本或稳定标签变化；
- 生产部署、回滚或 schema 迁移；
- 二期步骤由“本地通过”转为“候选通过”或“生产签收”；
- 应用更新源或开源观察对象变化。
