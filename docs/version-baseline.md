# Tick Stock Platform（TSP）版本基线

本文描述源码基线与身份确认方式。历次候选和现场记录独立保留于
[版本历史](version-history.md)，不可据历史文字推断当前部署。

## 1. 发布前已核实基线与身份获取

2026-11-19 工程优化以已验证的 **v0.4.67 /
`caf63b1b6e20ce5ee2aed663b7a39ea835b24af2`** 为父基线。
本轮是未发布源码变更，未分配新版本，未复核远端最新提交或两端实时运行身份。
最近已完成升级的证据入口见[升级记录](upgrade-20261118-four-hour.md)。

开发时使用该父基线的独立源码目录；旧工作区中的未提交内容需要另行核对，
不能用其旧 HEAD 代替正式父基线。进入开发目录后检查 `VERSION`、源码清单，
发布前再比对固定提交、构建清单与实际运行回执。

## 2. 当前功能与边界

应用版本以根目录 `VERSION` 及 `scripts/check_version.py` 为准。

| 版本维度 | 当前源码 |
| --- | --- |
| 应用语义版本 | `0.4.67` |

完整多租户部署使用 PostgreSQL 16，控制库和业务库迁移目标为 schema v8；
迁移器支持目标 v4～v8，实际运行 schema 必须另行读取数据库确认。
当前策略池定义为 `strategy_scope_v4`，它与应用版本及数据库 schema 分别管理。
完整职责见[当前架构](architecture.md#current-1-架构摘要)。

公共查询缓存、观测桶和后台共享职责的本次调整见
[工程优化说明](engineering-optimization.md)。自然交易窗口性能尚未签收。

## 3. 应用版本规则

保留现有 main CI 自动分配版本的机制；本地优化不手工递增版本，
不移动已发布标签。版本校验命令为 `python scripts/check_version.py`。

## 4. 交付身份与状态

源码修改、CI 验证、镜像构建、部署切换和自然交易窗口验收分别记录。
局部测试通过不能标记为已发布或已完成双端升级。
发布与恢复流程见[发布流水线](release-pipeline.md)。

## 5. 维护要求

当前规范只保留有效契约和事实源；日期回执写入独立历史页。
更新时运行 `scripts/check_docs.py` 和 `scripts/check_repository.py`，
并保留迁移 SQL 的既有校验和与用户设置。
