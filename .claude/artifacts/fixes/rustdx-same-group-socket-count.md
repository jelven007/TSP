# Rustdx 同任务组配额测试的连接计数修正

状态：本地修复并验证，PR全量CI待重新执行。2026-11-08。

## 问题与预期

S02修正的PR #52首次CI为5834通过、9跳过、1失败：
`test_same_task_group_cannot_multiply_its_budget_with_another_pool`观察到
`server.peak=10`，超过断言9。该测试及原生实现不在S02原始diff中。
预期仍为同组最多8条业务连接、同端点另加最多1条探测连接；
第二池不能扩增配额，第一池释放后第二池能够正常请求。

## 复现与根因

对原测试注入服务端EOF清理等待，连续3次在原断言失败，峰值均为11。
`_Server._accept`递增计数，`_handle`最终清理才递减；客户端已关闭的
串行探测连接仍可能留在该计数中。它不是客户端存活TCP连接数。

| 假设 | 验证结论 |
| --- | --- |
| 原生同组配额真实超限 | 未复现：原生配额始终8，独立系统TCP检查峰值9、探测结束后8 |
| 服务端清理滞后导致假超限 | 确认：同一故障夹具下客户端检查全通过，旧服务端断言11≤9失败 |

## 修正与兼容

将同任务组场景合入既有真实TCP配额用例，通过参数同时覆盖同组和不同组。
沿用端点去重、ESTABLISHED状态及可控EOF延迟，额外检查任务组峰值不超过8。
保留拒绝第二池、过程上限、结束状态及释放后恢复断言，不改生产实现或配额。
该方式沿用先前提交394d8271对不同任务组测试的修正。

## 验证

- 原测试受控复现3/3失败；新参数化用例2通过。

  该断言前的真实TCP峰值9、结束时8及业务配额8均通过。
