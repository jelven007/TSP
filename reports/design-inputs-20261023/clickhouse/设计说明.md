# TSP ClickHouse 十年历史数据表设计

基线：TSP v0.4.17，提交 cc837b95f471e5b299bf5e8618332d500bff7e3a。设计日期：2026-10-23。

范围：沪深股票为主的秒级采样、可信分钟 K、日频特征和历史信号筛选。以约 1 亿行／交易日、250 个交易日／年估算，十年约 2,500 亿行；实际按历史证券集合与交易日历计算。本文设计新查询存储，不修改当前 TSP 的数据或运行配置。

## 1. 设计结论与交付文件

采用“日频特征初筛、分钟范围索引定位、秒级明细精确复核、稀疏信号直接检索”的分层结构。事实表使用普通 MergeTree 语义保存不可变研究数据，不依赖后台去重或每次查询 FINAL。

物理上按月份分区，逻辑上按交易日发布数据段；查询必须先从固定研究快照解析所需 segment_id。单只证券查询走证券优先的排序键，全市场筛选走日期／分钟或信号定义优先的表。这样可以分别优化查询模式，而不复制整张秒级宽表。

| 文件 | 内容 |
| --- | --- |
| 01_schema.sql | 8 张逻辑表的单节点建表语句，可在空命名空间执行 |
| 02_cluster.sql | 自建集群版本：8 张复制表，其中 5 张事实表另有 Distributed 门面 |
| 03_queries.sql | 8 类带类型参数的查询示例 |
| 04_optional_projection.sql | 可选的秒级时间索引投影，不自动物化十年历史 |
| 05_quality_checks.sql | 6 类只读发布检查，需与导入控制层联合使用 |

01 与 02 是两种部署方式，不应在同一个已有数据库中连续执行。02 假设已配置 tsp_analytics、Keeper、shard／replica 宏和访问权限，不适用于 ClickHouse Cloud 的托管分片模式。本次只在隔离引擎验证 01 的行为，02 仅完成语法解析。

## 2. 表、粒度与访问路径

下表列出的“业务唯一键”由导入与发布控制层检查；ClickHouse PRIMARY KEY 不强制唯一。

| 表 | 一行的含义与业务唯一键 | 主要访问路径 |
| --- | --- | --- |
| instrument | 稳定证券身份；instrument_id | 代码与整数 ID 的映射 |
| instrument_state | 一个有效期在某次可知修订下的状态；segment、instrument、valid_from、record_version | 指定历史决策时刻的 ST、上市、行业、股本 |
| quote_second | 一只证券的一次实际采样；segment、instrument、capture_id | 单股／股票池的秒级时间段 |
| quote_1m_envelope | 一只证券一分钟内所有已保存样本的范围；segment、instrument、minute_start | 快速排除不可能命中的分钟 |
| bar_1m | 一只证券一根已完成、可信分钟 K；segment、instrument、bar_start | 分钟指标、分钟回测 |
| feature_1d | 一只证券一个交易日的一组已版本化日频特征；segment、instrument、trade_date | 十年日频筛选、行业／状态条件、因子研究 |
| signal_event | 一个固定定义的已识别信号；segment、event_id | 按规则、日期检索稀疏事件 |
| research_manifest | 一个快照选择某表／变体／交易日的哪一版本；snapshot、table、variant、segment_date | 固定并验证整个研究输入 |

以固定 6,000 只、2,500 个交易日估算，日频特征约 1,500 万行，一分钟一行约 36 亿行。分钟范围索引与可信分钟 K 是两份不同用途的数据，均需计入容量。秒级数据是否全部进入 ClickHouse、保留哪些列、采用哪种冷热策略，必须按查询负载与存储预算决定。

### 2.1 秒级明细的主键

```sql
PARTITION BY toYYYYMM(trade_date)
PRIMARY KEY (segment_id, instrument_id, observed_at)
ORDER BY (segment_id, instrument_id, observed_at, capture_id)
```

segment_id 先限定不可变数据段；instrument_id 连续组织证券历史；observed_at 支持半开时间窗口与有序回放；capture_id 保留同一毫秒多次采集的顺序。capture_id 不充当交易所逐笔序号。PRIMARY KEY 省去最后一项以控制稀疏索引大小，而磁盘仍按完整 ORDER BY 排序。

同一业务采样若出现两个不同 observed_at，应在发布前报错，不把时间字段加入去重规则后默认为两条合法采样。

### 2.2 日期优先的筛选表

feature_1d 使用 `(segment_id, trade_date, instrument_id)`。首期采用固定常用因子列，查询可以直接进行数值过滤，不需要将数十亿行指标拆成字段名／字段值形式再多次 JOIN。

quote_1m_envelope 使用 `(segment_id, trade_date, minute_start, instrument_id)`，适合指定日期／时段的全市场范围筛选。signal_event 使用 `(segment_id, definition_id, trade_date, event_at, instrument_id, event_id)`，适合固定规则的十年事件研究。

分区主要服务数据管理，真正的读取裁剪依赖排序键、列裁剪及较小的派生表。[1][2] 不按股票代码或交易秒做物理分区。

## 3. 字段与 TSP 的数据契约

### 3.1 类型选择

- instrument_id 使用 UInt32，由控制层分配，证券代码仍保存在 instrument。ID 永不复用，不用可能碰撞的临时字符串哈希代替身份。
- 时间使用 DateTime64(3, 'Asia/Shanghai')。从 epoch 毫秒导入时保留时间瞬间；现有分钟数据的北京时间 naive datetime 必须显式解释为该时区。不能把无时区值按服务器默认时区解释。
- 股票价格采用 Nullable(Decimal64(4))，金额采用 Nullable(Decimal64(2))；适用于本文的股票契约。导入须明确舍入政策、范围和溢出处理，不得静默截断超过精度的资产价格。
- 股数采用 Nullable(UInt64)，比例和指标采用 Nullable(Float64)。比例保留足够精度，未知值保持 NULL，零成交量与缺数据分开。
- 高频行只保留必要字段。Provider 名称、源码版本、转换版本和外部文件清单放在 segment 对应的 manifest 中，不在 2,500 亿行里重复存长字符串。
- 低基数字符串用于表名和变体名；证券名称／未知来源时间原文不一律声明 LowCardinality。

### 3.2 导入映射

| TSP 来源字段 | ClickHouse 字段 | 必须执行的转换／校验 |
| --- | --- | --- |
| collected_at_ms | observed_at | epoch 毫秒，作为实际采样可见时间 |
| capture_id | capture_id | 非负且保留原值；API 输出给浏览器时用字符串 |
| provider_ts_ms | provider_at | 保留来源语义，不能默认视为交易所时间 |
| source_ts_ms、source_time | source_at、source_time_raw | 保留原文及推断日期标志 |
| source_date_inferred | source_date_inferred | 推断时间不能标成 verified_snapshot |
| last_price、prev_close | 同名价格列 | 未复权价；非有限值转为明确错误或 NULL |
| open／high／low（秒级） | day_open／day_high／day_low | 这是日内累计 OHLC，不能用作该分钟 OHLC |
| 秒级 volume／盘口量 | cum_volume_shares／bid1_shares／ask1_shares | 按已验证的源单位由手转股；转换后校验整数与范围 |
| amount | cum_amount_yuan | 当日累计元，不能按每秒重复累加 |
| 秒级 change_pct／turnover_rate | change_ratio／turnover_ratio | 已规范为小数制时直接映射 |
| enriched turnover_rate | turnover_ratio | 当前是百分数值，显式除以 100 |
| enriched 的复权指标与 raw_* | 特征列与 raw_* 列 | 分开保存；记录 feature_price_basis 和复权锚点 |

0.03 表示 3%，0.05 表示 5%。不能用“数值是否小于 1”判断需不需要转换。

### 3.3 数据质量字段

quality_mask 建议固定为版本化位图：1=源时间未验证，2=源日期推断，4=采集缺口，8=非法价格，16=累计量额回退，32=输入重复，64=必需字段异常，128=证券／窗口覆盖不完整。新增位需更新契约。

input_valid 表示该行是否可以解释为有效观测，不等同于严格事件时间可用；源时间未知仍可能是有效接收快照。pit_eligible 表示派生结果通过约定的 Point-in-Time 检查，默认 0。缺失来源时间、首次采集前未知证券状态等不能因为入库成功而自动变成可信。

quote_1m_envelope 的 sample_count、expected_sample_count、max_gap_ms 和 boundary_gap 分别描述实际采样、计划采样与缺口。expected_sample_count 根据交易日历、采集窗口和实际计划计算，不对所有分钟硬编码 60，也不能只用行数证明时间覆盖。

## 4. 分区、分片、投影和索引

### 4.1 月份物理分区

十年常规数据约有 120 个月份分区。不同来源、逻辑变体和修订通过 segment_id 区分，不再增加高基数分区维度。历史数据按月分批导入，避免一次 INSERT 同时触及大量月份生成许多小 part。

同一个交易日可以存在旧、新两个 segment，但单个研究快照只能选择一个。修订某一天只重建该日数据，不重建整月。旧版本不被新版本覆盖。

### 4.2 集群按证券分片

五张事实表采用 `cityHash64(instrument_id)`。同一证券的秒级、分钟和日频数据在相同集群配置下落入同一 shard；跨证券筛选并行访问各 shard。

生产表使用 ReplicatedMergeTree，Distributed 门面复用原表名。instrument、instrument_state、research_manifest 是小表，完整复制到所有查询节点，不再套一层会把相同数据重复读出的 Distributed 门面。

每 shard 的 internal_replication=true；研究查询禁止 skip_unavailable_shards。增加 shard 或改变权重会改变新数据路由，必须迁移／重分片或定义新的路由代次后再发布，不能认为旧数据会自动搬迁。[6]

大规模回填可由受控导入器直接写 shard，路由必须与 Distributed 的分片权重计算完全一致。使用 Distributed 写入时区分后台队列确认与远端落地，按需要采用 distributed_foreground_insert；这仍不是跨 shard 的发布事务。

### 4.3 默认投影与可选投影

feature_1d 已包含 by_instrument 全列投影，替代排序为 `(segment_id, instrument_id, trade_date)`。它用于单股历史趋势和日频因子读取；该表远小于秒级明细，复制代价较可控。

秒级宽表默认不复制完整的第二排序。确有“某一秒附近全市场查看”的高频需求时，再使用 04 中的 `_part_offset` 投影，将键与行位置按 `(segment_id, observed_at, instrument_id)` 排序。[3]

此投影依然逐行存储键和偏移，在数千亿行上并不便宜；宽范围查询的回表 I/O 可能高于顺序扫描。新增投影只自动覆盖后续写入，旧分区需逐批 MATERIALIZE，并评估额外存储、写入、合并和恢复时间，不能一次性重写十年数据。

### 4.4 不默认堆叠跳数索引

不为每个浮点指标都加 minmax／bloom_filter。全市场股票混合后，一个 granule 内的数值范围可能很宽，minmax 无法跳过；等值布隆过滤器也不能加速任意数值区间。先用主键、范围索引表和因子宽表缩小扫描范围，再根据 EXPLAIN 与实际 read_rows 增加有收益的索引。

index_granularity=8192 是起测配置，不是本数据集的已验证最优值。变更为更细粒度须比较 marks、索引内存、压缩率与查询读取量。

## 5. 查询路径与正确性

03_queries.sql 使用原生 `{参数:类型}` 绑定。生产后端负责鉴权、请求边界和快照解析，不让浏览器直接取得 ClickHouse 凭据或任意拼接 SQL。

| 查询 | 目的 | 正确性边界 |
| --- | --- | --- |
| Q1 | 固定清单解析 | 每个要求的交易日恰好一个 segment；漏日属于缺数据 |
| Q2 | 十年日频初筛 | 截止该日结束，只用该截止前可得的日频输入 |
| Q3 | 生成可能命中的分钟集合 | 最大值只用于排除，不是最终信号 |
| Q4 | 在原始样本中同时验证阈值 | 输出有效采样命中，不证明真实逐笔触发 |
| Q5 | 回测 worker 读取指定证券／时间段 | 半开区间，有序输出，保留质量字段 |
| Q6 | 固定信号定义的历史分布 | definition_id 不允许改变语义；严格事件要求当时已可得 |
| Q7 | 历史证券状态 | 先筛可得时间，再选修订，最后判断有效期 |
| Q8 | 已完成分钟输入 | 未结束、尚不可得或未通过 PIT 检查的数据不参与 |

### 5.1 分钟范围索引不会代替精确判断

例如同一分钟第一秒涨幅 4%、换手 1%，第二秒涨幅 1%、换手 6%。该分钟两个最大值都能超过“涨幅 3%、换手 5%”条件，但没有任何一秒同时命中。Q3 保留这个候选，Q4 在同一行同时比较后剔除。

使用整分钟统计缩小离线扫描范围，只能作为不改变结果的物理优化。不能把该分钟结束后才知道的最大值作为分钟开始时的策略输入。范围索引必须来自清单选择的同一 quote_segment，验证覆盖完整且最值不会偏小；不具备安全排除依据时保留候选。

Q4 是有界窗口示例。处理十年候选时，后端先读取 Q3，把相邻时间段合并，再按 segment／instrument 分批调用 Q5 或等价直接范围查询。不要把全部候选塞进一条 GLOBAL IN；示例超过集合上限会抛错，不静默截断。

对于均线穿越、连续 N 秒、滚动波动等状态型策略，还须读取完整预热窗口并保留事件顺序，不能只把命中点送入回测。共享资金组合仍由回测引擎按时间推进。

### 5.2 历史可得时间与数据修订

available_at 表示数据在研究的历史时点何时可知；published_at 表示当前数据库何时发布这份研究版本。后者不能替代前者，也不能简单把过去行情的数据库导入时间当成当年的事件可得时间。

instrument_state 同时保留有效期和修订可得时间。Q7 在决策时间前筛选，再用包含整个状态的 tuple 做 argMax，确保最新修订中的 NULL 不被旧非空值“补回去”。同一决策时间下出现重叠有效期必须在发布时拒绝，不能在读侧任意挑一条。

TSP 现有 SCD2 历史只覆盖已采集范围。若原文件缺少过去修订的可得时间、后续补写 valid_to 的可知性或历史股本证据，就不能虚构 record_version／available_at 来声称严格 PIT。首次采集前未知状态保持不可用；研究必须保存具体降级说明。

日频 MA／波动率等修订可能影响后续窗口，EMA 等递推指标还会持续影响后续结果。重建哪些日期应由因子依赖决定，不能只更新原始行情的那一天。复权政策、有效锚点和历史成分也纳入版本。

## 6. 幂等导入与原子发布边界

### 6.1 版本模型

segment_id 是不可变数据段标识，对事实表对应“表 + 变体 + 交易日 + 修订”。一个 segment 必须包含该逻辑范围的完整记录；不是每次 INSERT 生成一个 segment。instrument_state 较小，可一次发布完整历史版本，并使用 1970-01-01 作为清单中的维表日期。

snapshot_id 选择一组 segment；新快照可以复用绝大部分旧 segment，只替换被修订的日期。清单通常是几千至几万行，远小于事实表。相同 snapshot 的清单不追加修改。

分段发布流程：

1. 在控制库分配新 segment，冻结源文件清单、证券集合、日期、转换代码和输入契约。
2. 规范化、去重并批量写入尚未对研究开放的 segment；大规模回填逐月调度，控制小 part 数量。
3. 执行唯一键、行数、数值单位、缺口、时间、证券状态和派生索引一致性检查。05 提供 SQL 子集。
4. 核对每个 shard 的落地数据，以及全部可能承担读取的副本是否具备完整数据；不完整副本须暂时从可读集合排除。
5. 构建完整不可变 manifest，镜像到全部查询节点并确认一致。只有数据与清单均就绪，TSP／PG 才把 snapshot 标记为可用。
6. 查询入口仅接受控制库已发布的 snapshot，任务全程固定该版本。中途失败或未发布的数据不能被“查询最新”读到。

ClickHouse 没有自动提供上述跨表、跨 shard、跨系统发布事务。02 只建表，不替代导入控制器、发布屏障或故障演练；这些是后续接入 TSP 时必须实现的协议。

### 6.2 重试与重复

ReplicatedMergeTree 的插入去重有有限窗口。[4] 批次使用稳定内容摘要和 insert_deduplication_token，记录导入台账；相同 token 的数据内容必须一致。它可以缓解短时间重试，但不能当作永久业务唯一约束。

写入结果不明且已超出可证明的去重范围时，核对原段，或放弃尚未发布的 segment 并以新 ID 重建；新快照只引用通过完整校验的一份。发布检查必须能发现跨批重复、同 token 不同内容和同 capture 时间矛盾。

本方案没有默认使用 ReplacingMergeTree。它的去重发生在后台合并，不能保证查询时不存在重复；旧版本也可能在合并后丢失，影响固定历史研究。[5] 因此研究正确性不依赖“等一会儿合并完成”。

### 6.3 为什么没有把所有聚合写成增量物化视图

增量物化视图处理新插入的数据块，并不会因上游修订、分区替换或后台去重自动撤销旧聚合。[7] 本方案先从已校验的原始 segment 构建完整的日段派生数据，再一起发布，避免重复导入放大计数与成交量。

后续如给在线实时统计增加 AggregatingMergeTree／物化视图，应单独定义重试、去重、迟到和重建机制。历史日频 MA、行业分类、可得时间和信号状态仍不能简单由每个插入块独立推算。

## 7. 容量、冷热分层与性能验证

按 2,500 亿行估算，若实测压缩后每行 50／100 字节，单份秒级主体约 12.5／25 TB。该算式不包括副本、索引、投影、派生表、修订和对象存储中的 Parquet 原始数据；也不是压缩率承诺。

DDL 没有自动删除 TTL，避免误删十年研究或被旧快照引用的数据。冷热移动通过部署的 storage_policy 和存储层实现；ClickHouse 对象存储中的 MergeTree 数据与原始 Parquet 是不同格式，不能直接共用同一批文件。配置上线前须单独核实对象存储、权限、缓存、恢复与费用。

旧 segment 的清理依据任务／快照引用和保留政策。月分区内可能混有多个日期的有效版本，不能只因为其中一个版本过时就 DROP 整月分区；长期整理可离线生成新的物理数据集后受控切换。

引入索引或扩大分片前，用代表性真实数据完成以下对照，不从小样本推断生产延迟：

- 单股／百股的一日和一年秒级读取；
- 十年日频多条件筛选；
- 某天某时段全市场分钟候选与精确秒级复核；
- 固定信号定义的十年查询；
- 已缓存与未缓存、冷热存储、并发研究与历史导入期间的差异。

记录 EXPLAIN indexes=1、read_rows、read_bytes、query_duration_ms、峰值内存、网络量及结果一致性。不能只报告服务端 LIMIT 100 返回快，而忽略候选生成和完整结果读取。

```sql
EXPLAIN indexes = 1
SELECT observed_at, last_price
FROM tsp_history.quote_second
WHERE segment_id = {quote_segment_id:UInt64}
  AND instrument_id = {instrument_id:UInt32}
  AND trade_date = {trade_date:Date}
  AND observed_at >= {time_from:DateTime64(3, 'Asia/Shanghai')}
  AND observed_at < {time_to:DateTime64(3, 'Asia/Shanghai')};
```

批量写入应以实测行数／字节预算控制，避免每只证券一个 INSERT。可从每批数万至数十万行起测，按行宽、内存、延迟和 part 增长调整；导入吞吐与后台合并、在线查询之间保留资源余量。[8]

## 8. 对 TSP 的接入边界

秒级入库复用 SecondQuoteArchive 已发布分片及其时间字段；不新增第二套行情采集。分钟源经当前 Provider 能力路由和标准化层，不能从采样秒级最值冒充权威分钟线。

研究查询新增受控 ClickHouse 仓库适配，由现有 services／worker 调用；API 保持薄层。研究任务保存 snapshot_id、变体、证券集合、参数／代码摘要、可得时间政策及质量结果。前端仍使用现有请求客户端与缓存键，并把 snapshot_id 纳入研究结果缓存。

当前 SecondQuoteReplay 的短窗口、文件摘要和因果校验仍可用于基准对照。新的 ClickHouse reader 应与 Parquet reader 在同一已知样本上逐行核对，再比较回测结果；不能只扩大日期上限或把所有明细 collect 到一张内存表。

信号查询只负责提供事实输入和候选；订单状态、组合现金、费用、T+1 与跨日持仓继续由回测引擎处理。ClickHouse 不是交易账务数据库。

## 9. 本次实际验证

验证环境：macOS 的隔离 chDB 3.7.2，内部 ClickHouse 25.8.2.1。验证数据是手工构造的极小 SQL 正确性夹具，不是市场样本，也没有用于吞吐、压缩率或延迟宣传。

已通过 26 项检查，覆盖：

- 8 张表实际创建；5 张事实表的集群门面及复制 DDL 完成语法解析。
- `_part_offset` 可选投影实际创建。
- 8 类查询与 6 类发布检查实际执行。
- 日频筛选排除晚到／未知输入、ST 和跨月不匹配记录。
- 分钟范围最大值发生在不同秒时，精确复核不会误判同时命中。
- 时间窗右端排除、未完成分钟不可见、信号可得时间检查。
- 历史状态修订不穿越时间，最新状态中的 NULL 不被旧值替代。
- 新 segment 发布后的旧 snapshot 结果保持不变。
- 重复采样、错误范围索引及不成立的 PIT 声明被检查发现。
- 查询计划存在 PrimaryKey 索引分析。

未验证：真实数据装载、2,500 亿行性能、Keeper 与复制恢复、跨 shard 查询结果、对象存储策略、跨系统发布屏障及 TSP 集成。集群 DDL 解析通过不等于高可用部署已通过。
