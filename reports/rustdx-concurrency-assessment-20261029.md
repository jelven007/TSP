# rustdx 并发连接配置与取数链路评估

核对日期：2026-10-29。源码基线：v0.4.38 / `5b273174f2e2a8ac539fcea363fa02315a61ebe9`。
本文件记录设计评估；新增设置和多主站并发尚未实施。现有工作区修改和运行配置保持。

## 配置契约

系统设置页在“并发策略”下方新增独立的“并发连接”区域，仅包含两个可编辑参数。
配置属于平台全局资源，由具有 `settings:manage` 权限的管理员维护，沿现有 API→Platform 转发和 preferences 原子合并写入，不保存为浏览器本地偏好或租户独立连接预算。[设置入口](../frontend/src/pages/settings/System.tsx#L116-L137)、[权限与转发](../backend/app/multitenancy/access.py#L100-L152)、[平台管理路径](../backend/app/multitenancy/platform.py#L41-L63)已核对。

| 参数 | 默认值 | 范围 | 推荐含义 |
| --- | ---: | --- | --- |
| 单主站连接数 | 9 | 用户未指定；建议首版为2～9 | 每个主站的TCP连接总上限，其中固定1个探测配额，其余为业务配额 |
| 多主站并发数 | 4 | 1～5 | 同时连接的不同主站数量上限；健康节点不足时实际数量允许降低 |

“2～9”是首版建议，保留当前每主站8个业务连接的保守上限，并非已确认的主站协议硬限制。1个总连接会被固定探测配额占满，没有业务连接，因此不建议允许1。后续扩大单主站上限应先验证主站拒绝率和吞吐拐点。

设单主站总连接上限为C，主站并发上限为H，则业务容量上限为 `(C−1)×H`，探测容量上限为H，总容量上限为 `C×H`。这是容量算式，不是耗时预测；探测配额按需使用，不要求长期占用一个TCP。

| 单主站上限 | 主站上限 | 业务连接容量 | 探测连接容量 | 总TCP容量 |
| ---: | ---: | ---: | ---: | ---: |
| 9 | 1 | 8 | 1 | 9 |
| 9 | 2 | 16 | 2 | 18 |
| 9 | 3 | 24 | 3 | 27 |
| 9 | 4 | 32 | 4 | 36 |
| 9 | 5 | 40 | 5 | 45 |

建议按用户所说“同时连接的主站总数”严格计数：探测、业务及财务专用连接不能通过不同连接池绕过主站数量和单站限额。站点身份采用规范化的实际IP与端口，重复地址不能当作不同主站。若财务端点独立于行情端点，它也占用一个站点位置；其财务心跳资格仍与行情资格分开验证。

达到H个已连接主站时，不能再同时探测第H+1个候选。主动换站需要先在安全边界退役并关闭原站连接，再探测、接入替代站。配置是上限，实际建立连接数和当前可用主站数应另行回显。

单站C=2、H=1时只有一个业务槽，实时与历史任务只能有界串行或在安全边界公平轮转，不能同时保证两个独立预留槽。页面应明确这一低容量状态；默认9/4方案仍按前后台隔离与公平性验证。

## 当前实现的限制

| 核心网络/探测策略及桥接初始化使用OnceLock | 重建Python客户端不能改变已初始化的全局预算 | [网络策略](../backend/native/rustdx_native/vendor/rustdx-core/src/tcp/governance.rs#L98-L140)、[探测策略](../backend/native/rustdx_native/vendor/rustdx-core/src/tcp/ip/coordinator.rs#L44-L53)、[Python重建](../backend/app/plugins/rustdx/client.py#L60-L92) |
| 共享许可目录保存固定容量，不同容量会被拒绝 | 多进程改配置必须协调，不能仅换目录绕开旧连接计数 | [共享容量校验](../backend/native/rustdx_native/vendor/rustdx-core/src/tcp/governance.rs#L377-L427) |
| 分钟取数采用静态证券分组，每组内串行分页 | 单证券慢请求会拖住整组；多站增加后需改善任务分配 | [分钟分组](../backend/app/plugins/rustdx/provider.py#L725-L799) |
| 原生池接口和Python可用性检查固定API3及8/1身份 | 单独替换Rust文件或旧wheel会被拒绝或产生契约漂移 | [桥接导出](../backend/native/rustdx_native/src/lib.rs#L831-L846)、[身份检查](../backend/app/plugins/rustdx/client.py#L96-L125) |

以上属于源码和既有回归确认。当前实际部署是否启用跨进程共享许可目录，本轮未读取运行凭据或远程环境，不能把可选机制描述为已经全主机启用。

## 必须同步改造的链路

| 优先级 | 环节 | 改造要求 | 验收依据 |
| --- | --- | --- | --- |
| P0 | 设置与持久化 | 两参数严格整数校验、全局保存、管理员权限；保存值、当前生效值和主站不足状态分开反馈 | 刷新/重启保留，普通租户不可改，错误保存不覆盖旧值 |
| P0 | 原生连接与预算 | 每主站独立业务槽与探测配额，同时执行全局TCP上限、主站数量上限和单站上限 | 业务、探测、财务、重连、冷启动以及多进程均不能突破预算 |
| P0 | 主站调度 | 从合格节点中组成活动集合，按实际业务响应时间、错误率、在途请求负载分配证券任务；不同槽不再统一跟随一个主站指针 | 四主站确实同时承担业务，一个节点失败不导致健康节点全体换站 |
| P0 | 配置生效 | 扩展底层可更新预算能力，或明确采用协调排空后重启；不能假装重建Python对象就完成热更新 | 降配、扩容、失败回退和跨进程变更后，实际计数与生效值一致 |
| P0 | Python Provider | 线程容量由当前可用业务槽派生；沿同一预算控制日K、分钟、实时、股本、除权和财务入口 | 不残留8/7常量形成第二个隐式上限，不因多个调用各建线程池而无限排队 |
| P0 | 来源与分页 | 同证券同窗口的分页、定位页和重采绑定主站、连接身份和配置代次；证券之间并行 | 源变化时丢弃旧局部结果完整重采一次，持续变化拒绝不完整历史 |
| P0 | 原生身份与交付 | 同步PyO3接口契约、Python身份检查、核心适配补丁清单、冻结构建及各平台wheel | 旧桥接明确拒绝不支持的配置，新产物与固定源码/锁/补丁身份一致 |

建议使用类似 `connections_per_host` 和 `max_hosts` 的新字段，避免把“总数9”错误传给旧的“业务连接数”参数。新设置API可沿现有GET/POST习惯设计为 `/api/settings/rustdx-concurrency`；这是拟议契约，当前仓库没有该API。

旧环境变量应区分启动默认与显式用户覆盖，保持兼容解释。例如旧 `RUSTDX_QUOTE_CONNECTIONS=35` 当前实际被限制为8，不能迁移成单站36个连接。新配置需要取消默认线程8、后台7的隐式限制；显式用户限制仍保留，并显示实际生效容量。

现有 `/api/settings` 管理路径已统一转发Platform，因此无需另建平行转发通道。无需新增数据库schema或业务Provider数据集。扩展当前锁定的rustdx v2.0.4本地适配和原生桥接即可推进，不应把更换上游版本或改成异步框架作为这项功能的前置条件。

## 配置变更与实时任务保护

推荐支持安全生效：先验证并保存目标配置；当前已开始的证券分页保持原来源与参数，在证券或业务批次安全边界退休旧槽；预算与活动站集合达到新限制后才报告新配置已生效。降配时先停止给退休槽分配新证券，已有分页完成后关闭连接；不能在保存设置的同步请求中等待整个历史任务或直接断开它。

原生网络预算的一次性初始化必须明确处理。推荐改为可调整准入上限、保留所有存量许可真实计数的控制机制，缩小预算时等待存量连接退役。如果首版选择重启方案，页面必须显示“已保存，排空并重启后生效”，且自动化协调需覆盖所有真实网络使用进程。不能将新旧代次放入各自独立许可目录后相加突破总上限。

业务槽包含实时行情和后台历史采集，32个业务槽不等于32个历史任务槽。推荐保持至少一个实时预留槽和后台最低保障份额；默认四站时，如只预留一个实时槽，历史并发理论上最多31路，再按资源、显式限制和可用主站降低。不要把后台最低保障实现为无条件绝对优先，也不要让持续实时查询把后台永久饿死。[当前调度器](../backend/native/rustdx_native/src/pool.rs#L39-L140)已有实时槽预留和后台份额机制，升级应保留其两侧不饥饿契约。

## 进一步提高速度和效率的优化

| 优先级 | 优化 | 原因与范围 |
| --- | --- | --- |
| P0 | 按证券任务动态分配 | 用有界任务队列替代固定分组；空闲槽领取下一证券，慢证券只占自己的槽。保留单证券分页串行和来源绑定，取消后不再启动新任务 |
| P0 | 证券分页使用持续租约 | 当前expected_source能检测来源变化，但槽租约按单页释放。建议证券窗口持有稳定租约，减少其他请求复用同槽引发的重采；归还、异常和取消都必须释放 |
| P1 | 按业务质量选站 | 当日三轮资格验证继续保留；排名加入实际K线/快照响应耗时、数据覆盖度及错误率。握手测试耗时不是业务吞吐指标，最近日期可用也不证明历史月份完整 |
| P1 | 分阶段预热与连接复用 | 合格主站逐步建连，避免一次打开36个TCP；缓存当日资格与已认证元数据，持续复用业务连接。显式主站名单不擅自扩大，健康不足时回显实际数量 |
| P1 | 控制故障恢复负载 | 单站冷却、有限重试及带随机抖动的退避；关闭旧连接后再建替代连接，健康主站保持服务。探测失败不触发所有业务槽重建 |
| P1 | 保留少请求的历史算法 | 继续100证券/最多32自然日、跨日共享定位、准确缺口相交、无缺口零请求及闭市跳过。并发升级不能退回每日重复分页，也不对已完整证券重复补采 |
| P1 | 让容量变化可观察 | 输出每站开连接/在途请求/等待数、当前主站集合、配置值与生效值、排队P95、传输P95、失败率、返回行和业务请求计数。已有核心统计需透传，避免把开连接数当作并发请求数 |
| P2 | 根据CPU分析减少序列化 | `bars_json`带来源结果存在先编码行数组、再解码嵌入结果后再编码的路径；先评估减少原生重复JSON处理。只有确认边界转换是瓶颈后，再考虑批量原生接口或Arrow |

原生接口已通过 `py.allow_threads` 释放网络调用期间的GIL，因此不能直接把取数受限归因为“Python无法并发”。先让连接预算、任务调度和Python线程数一致；增加线程后的帧转换、排序、Polars拼接和内存峰值再用CPU/内存证据评估。

元数据可以继续共享，但需验证各活动主站的证券与价格精度基准一致；不一致时按主站隔离或拒绝该节点。历史页面缓存继续局限于单次证券取数，不能把不同主站或不同配置代次的定位结果混用。

## 性能目标、容量与验证

当前四主站方案尚未实现，四站吞吐、P95、资源拐点和故障后恢复耗时均未知。既有v0.4.38正式100证券/2026-08-03～08-31样本为504,000唯一键，本地遗漏14.366秒、ECS遗漏11.878秒；这些是单次正式样本，不是四主站性能、全市场耗时或P95。[既有部署证据](minute-collection-reliability-20261029/deployment.md)和[原始前后对照](minute-collection-reliability-20261029/benchmarks.json)分别保留不同测试阶段。

建议验收边界按以下顺序确定：

1. **用户边界目标**：从正式HTTP任务创建至持久终态计时；分别报告全量/遗漏吞吐与端到端P95。初始门槛建议四站任务P95不高于同环境一站基线、实时快照P95增加不超过10%；绝对秒数尚未设定，不能承诺四倍提速。
2. **负载方法**：以相同证券、日期、字段和独立目标目录进行真实取数对照，先比较H=1～5，再对选定配置重复至少20轮估算样本P95；兼顾冷热启动、盘中快照＋分钟＋财务并行、突然批量请求和30分钟持续运行。协议故障用本地TCP测试验证；协议模拟不作为公开主站容量证据。
3. **资源余量**：建议至少保留20%CPU和内存余量，以实际Platform容器限制为边界。持续记录连接池等待时间、等待数与最老等待年龄、CPU、RSS、网络、错误率和队列排空速率，找到增加主站后吞吐不再增加或P95/失败率明显恶化的位置。
4. **过载保护**：停止增加后台准入，不因超时继续扩容或扩大重试；优先保留实时快照/交互查询，同时维持后台最低份额。前台持续积压时减少后台新证券派发，已开始的分页继续受原时限约束。
5. **异步队列**：建议待派发队列上限为有效worker数量的2倍，超出时由生产者等待而非无限提交；记录队列深度、最老年龄和完成速率，取消后立即停止新增工作。
6. **热点分析**：网络队列、固定证券分组、来源重采、元数据预热锁及原生/ Python转换是主要核对点。按分段计时区分定位、入槽等待、传输、转换、合并和写盘，再决定后续优化。
7. **后台预算**：测速、预热、财务和历史补采计入同一连接预算；并发增加不能挤占Platform前台服务或更改用户的策略资源配置。新节点按业务槽批次逐步加入，控制器缺少统计时保持已验证容量。

| 场景 | 通过条件 | 停止/回退条件 |
| --- | --- | --- |
| H=1～5、C=2/9及非法输入 | 严格校验，实际单站/站数/全局计数不超限，保存与生效回显一致 | 计数超限、保存值与实际预算不符 |
| 同样本full/missing、重复运行 | 唯一键、OHLCVA、价格基准与必要缺口一致；无缺口零业务请求 | 混源、重复键、值错误、为提速隐藏缺口 |
| 慢主站、断连、资格失效 | 健康节点继续工作，重采不混旧页，重连不突破H或C | 全池同步换站、重试放大、无限等待 |
| 盘中快照与历史/财务并行 | 实时P95回退不超过建议10%，后台持续有进度 | 实时饥饿、后台停滞、CPU/内存持续无余量 |
| 4→1、9→2及快速反复改值 | 当前分页完整结束，退休槽排空，取消及时，最终只报告实际生效值 | 直接断开业务、来源错配、旧新许可相加超限 |
| 多进程及进程崩溃 | 按主机/站点协调许可，进程退出释放，消费者不重复开采集池 | 每进程各自增加36个连接，许可泄漏或不同配置互相绕过 |
| 超载后恢复 | 队列有界且可排空，错误率和吞吐恢复；记录实际恢复耗时 | 未测出拐点或恢复能力却宣称容量验收完成 |

## 本轮实测与实施边界

本轮仅执行当前代码的契约回归，命令为：

```text
python -m pytest tests/test_rustdx_provider.py tests/test_rustdx_native_pool.py -q
```

使用独立临时DATA_DIR/PLATFORM_CONFIG_DIR、`TICKFLOW_ENV_FILE=/dev/null`、standalone模式和有界Polars线程。结果为 **68 passed，27.29秒，exit 0**，包含当前8连接限制、配置变化、来源保护、真实本地TCP与池回收等契约。不是新增多主站方案已通过，也不是公开主站压测。

实施建议分为两个可验证批次：第一批完成两参数及所有P0链路，包括必要的来源、预算、实时保障、配置生效、指标和回归；第二批根据真实对照补充选站质量、预热、动态资源调整及序列化优化。动态证券分配宜随第一批完成，才能避免新增连接长期闲置。

应用版本继续由远程main CI分配。正式升级需要匹配前端、Python、原生核心适配和wheel/镜像，先验证固定身份与回归，再按既有本地/ECS发布流程验收。多主站不会自动解决上游已不保留的历史，既有5,520历史键及最近未返回键仍应以实际取数和缺口报告为准。
