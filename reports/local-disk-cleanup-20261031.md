## 实际操作

1. 核对运行进程、数据库、镜像、源码恢复集合、工作树和任务引用。修复项目从 TSPP 改名为 TSP 后失效的 Git 工作树链接，重新检查所有工作树；失败的 `git status` 没有被当作干净状态。
2. 使用 Cargo 清理两个已确认的 Rust 构建目录，回收确认闲置的 Python/Node 依赖和 Rust 输出。仍由进程使用的临时运行副本保持原样。
3. 删除 16 个旧 OCI 镜像导出包以及 6.818 GiB 的下载 blob。对备份内字节、权限和时间一致的不可变文件核对 SHA-256 后建立硬链接，保留原路径和内容，去重约 3.14 GiB。数据库与行情备份的原路径和内容保留。
4. Docker 镜像由 48 个整理为 11 个，保留当前版本及两个回滚版本的运行/计算镜像。构建缓存由 13.7 GB 降至 4.968 GB。Colima 数据盘内执行 `fstrim`，宿主机文件的分配块由约 49.25 GiB 降至约 23.98 GiB。
5. 应用发布副本从 15 份整理为 3 份。移除两个闲置且干净的 rustdx 工作树，以及确认闲置的 TSP 干净工作树；移除前保留 HEAD 引用。未提交代码按下文方式保护。公开行情快照按引用检查后分批回收。
6. 执行 `uv cache prune` 和 `pnpm store prune`，分别移除 121,634 个缓存文件、15,117 个文件及 328 个包。uv 缓存分配块从 5.220 GiB 降至 2.232 GiB，pnpm store 从 0.248 GiB 降至 0。TRAE 通过原生 Resources Explorer 清理代码索引和 10 份历史问答快照；快照从 133.96 MB 降至 1.43 MB，保留当前会话快照，历史问答内容仍在。日志入口没有可选条目、清理按钮禁用，运行日志保留。

以上目录计量有硬链接、APFS 共享块及重叠口径，不能相加作为整盘释放量。Docker 的 GB 采用引擎输出口径；GiB 按 1024³ 字节换算。

## 公开行情快照的保护规则

本次回收使用本机独立维护脚本，没有改变运行应用源码：

`~/.local/share/tsp-dev/maintenance/public_snapshot_gc.py`

脚本默认只出计划，带 `--apply` 才删除。本次保护：

- 动态读取的 `public/current`、最近 24 小时的成功发布和所有数据库中的历史任务引用，包括成功及失败的研究输入。
- 在业务库和控制库只读扫描 JSON/JSONB 字段；保留找到的 9 个数据库引用版本。
- 离线 JSON 证据中的公开版本引用、打开文件中的版本引用，以及进程启动附近的版本。
- 不碰发布器的隐藏 staging 目录；缺少有效清单、存在额外文件或符号链接的候选目录不删除。
- 每 10 个候选重新核对引用，每次删除前重新检查 `current`；清理前后对当前快照全部文件校验 SHA-256。

路径越界、清单路径穿越、不完整校验清单、额外文件/符号链接、数据库不可用的 5 个失败边界检查已通过。本批实际删除 **285** 份快照，复核中跳过 8 份；发布器继续运行，回收结束时共有 **236** 份成功发布目录。清理前后各对当前版本的 **13,455** 个文件完成 SHA-256 校验。

手动运行：

```bash

  "$HOME/.local/share/tsp-dev/maintenance/public_snapshot_gc.py"

  "$HOME/.local/share/tsp-dev/maintenance/public_snapshot_gc.py" --apply
```

没有建立定时任务。脚本针对当前本机部署路径和本地 PostgreSQL 连接；数据库、运行目录或快照引用契约变化后应先重新核对。
