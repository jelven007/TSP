# rustdx 并发连接性能验证

2026-10-29；固定基线 v0.4.38 / `5b273174f2e2a8ac539fcea363fa02315a61ebe9`。

**结论：暂缓全面升级。** 四主站原型能够分流并遵守实验进程的连接预算，但历史分钟数据一致性检查未通过。仅扩容连接、上层仍用8线程时，预热取数没有显示提速。不能据此发布默认四站并发，也不能承诺32线程的收益。

所有取数、缓存、编译和源码实验在隔离目录执行。没有修改本地或ECS运行配置、生产行情、设置页面或应用版本，没有提交、推送或部署实验代码。

## 实测范围

真实输入为既有正式样本的100只证券，2026-08-03至2026-08-31的1分K，每次返回504,000个唯一键。比较`symbol/datetime/open/high/low/close/volume/amount`，保留原始价、北京时间及单证券分页来源保护。

环境为同一台macOS主机、Python 3.12、12逻辑CPU、36GiB内存，Polars固定4线程。按当前源码复制基线Python模块；基线使用既有原生桥接，原型使用隔离wheel。锁定的rustdx v2.0.4及全部109个核心文件逐文件一致，没有更换上游或修改解码器。

| 参数 | 当前单站基线 | 四站控制组 |
| --- | ---: | ---: |
| 每站总连接目标 | 9 | 9 |
| 业务槽容量 | 8 | 32 |
| 探测上限 | 1 | 4 |
| Provider线程 | 8 | 8 |
| 后台准入上限 | 7 | 31 |
| 实际后台请求峰值 | 7 | 8 |

四站控制组用于判断“只增加连接、线程仍受原8路限制”的效果。32个已打开业务TCP包含空闲连接，不能当作32个在途请求。原型仅按槽固定分配主站，在新进程中设置预算；没有实现产品配置、热更新、跨进程预算或自动替换故障主站。

## 数据一致性阻断

单站冷、热结果完全一致，规范CSV的SHA256为：

```text
6c04f44b1908501ad459a96948f332e2ef7b455fe0134143b68a6c69ac0fb9a4
```

四站首次冷结果与该基线有**1,891个键值不同**。随后四站诊断进程自身的冷、热结果有**2,799个键值不同**；两次均有504,000个唯一键，来源检查和网络错误计数均未报错。这说明“相同行数、无异常、分页内来源不变”不足以保证历史值一致。

| 四站诊断冷/热差异字段 | 不同键数 | 最大绝对差 |
| --- | ---: | ---: |
| open | 904 | 1.20元 |
| high | 209 | 0.81元 |
| low | 213 | 0.94元 |
| close | 795 | 1.16元 |
| volume | 2,696 | 25,867手 |
| amount | 2,714 | 7,567,400元 |

这些字段差异存在交集，不可把键数相加。差异包含相邻分钟之间成交量、成交额的转移，不只是浮点尾差。

例如`300206.SZ`的2026-08-19 10:29，当前主站返回249手、295,062元，另一主站返回230手、272,547元；10:30则分别为585手与604手。四站来源记录还显示，同一证券的两次任务可分配到不同主站，例如`002612.SZ`从`110.41.147.114:7709`变为`117.34.114.13:7709`。这发生在两次完整窗口之间，不能归咎于单次分页混源。

### 逐站和原始协议复核

12个候选中4个通过三轮协议资格验证并返回800条真实近期分钟记录；其余8个未通过。本轮没有找到第5个合格节点。近期页通过不代表目标历史窗口一致。

对6只相关证券逐站读取同一月份，每次30,240键，使用未修改的基线桥接：

| 主站 | 两次同IP输出的不同键数 | 首次输出与当前主站的不同键数 |
| --- | ---: | ---: |
| 117.34.114.13:7709 | 0 | 0 |
| 115.238.56.198:7709 | 266 | 214 |
| 180.153.18.170:7709 | 80 | 129 |
| 110.41.147.114:7709 | 0 | 121 |

当前主站的这6证券输出也与100证券基线的对应切片完全一致。此项仅认证本轮这些样本，不判定其他主站哪个历史版本正确。

为排除Python/Rust解码变化，额外用独立TCP脚本发送相同协议请求，校验响应魔数、命令、消息号及解压长度，采集`688721.SH`的48份解压后响应体：4个IP，每IP两条顺序TCP会话，每会话重复两轮，每轮3页。任一时刻仅打开一个该脚本的TCP。

| 分页start | 每次返回条数 | 首条时间（全部相同） | 不同响应体SHA256数量 |
| --- | ---: | --- | ---: |

其中115和180两个IP在不同TCP会话间各返回两个历史响应体版本，同一TCP内重复页稳定。差异已存在于解码前的主站响应，不能靠提高线程数消除。没有进一步识别服务端分片、行情版本或权威分钟归集规则，不能把任一版本自动认定为错误或擅自折算覆盖已有行情。

## 连接与验证证据

本地使用4个真实TCP测试端点。旧桥接虽探测4站，128次业务请求全部落在1站；原型128次请求分布为36/32/32/28，4站均承担业务。业务TCP峰值32、探测峰值4，每站观测峰值8，64个证券来源在后续分页保持一致。业务与探测峰值发生在不同阶段，不表示同时实开36个TCP。

真实四站控制组的两次取数业务请求按主站分布为714/700/686/700，每站成功来源覆盖8个独立业务槽；网络失败、来源变化及快照错误均为0，但数据值一致性仍失败。

上述预算证据覆盖实验进程和本地TCP端点，不证明全主机、多进程或与运行中Platform合计的连接数符合拟议上限。

## 后续决策与未执行项

保留当前运行配置。后续先把主站资格从“近期页可返回”提升为“目标历史窗口、不同TCP会话的OHLCVA及价格基准可验证一致”；按证券、窗口和行情版本选择经过认证的来源，合格站点不足时回显实际可用站数。持续租约仍有价值，但只能保护一个窗口内的TCP身份，不能单独解决会话之间的历史版本差异。

该数据门通过后，再同步扩容原生预算与Provider线程，比较8/16/24/32路，以及动态证券队列和单站质量控制组。当前连接扩容后上层仍8线程的结果，不能代表完整32路方案的性能。

本轮数据硬门失败，按预先设定的停止条件，没有进入四站32线程真实压测、2/3/5站拐点、20轮交替任务P95、服务持久化/无缺口验收、全市场快照混合负载、30分钟持续运行、ECS性能对照、故障站替换、配置热更新、多进程或正式发布。没有把这些未执行项包装为通过；它们属于后续实现和升级验收。
