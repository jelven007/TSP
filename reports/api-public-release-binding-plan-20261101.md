# 闲置API发布绑定修复方案摘要

日期：2026-11-01。方案已形成，待实施；本轮没有修改应用源码或生产环境。
上述状态描述原方案阶段。用户随后批准实施，当前源码及验证结果见
[实施记录](api-public-release-binding-implementation-20261101.md)，生产尚未切换。
完整任务、接口边界、验收、风险及回滚见
[实施方案](../.claude/artifacts/plans/api-public-release-binding-sync.md)。
已确认的生产故障与复现见[根因调查](api-readiness-root-cause-20261101.md)。

推荐每个API进程在生命周期内启动一个发布巡检线程，默认每5秒比较current和
已提交仓库。发布没有变化就结束；仅发布变化时复用现有刷新锁和PublicMarket
准备新仓库及快照，成功后用短更新锁提交。行情marker增长不会让闲置巡检
反复拉取完整快照。健康检查只捕获已提交的一致视图，不承担大快照下载。

利用已有不可变`.public_release.json`作为共享锁对象：
API仓库持有只读共享锁，旧仓库仍有在途引用时继续保留锁和DuckDB连接；
维护删除前取得同一文件的非阻塞排他锁，并再次检查current和研究引用。
锁忙、文件或能力异常时跳过删除，不需要新增数据库租约表或改清单格式。

候选环境目标为4个闲置进程在25秒内完成绑定更新；无变化12轮快照调用增量为0。
准备失败保留旧完整绑定，同步持续失配或巡检失活超过30秒如实返回503。
30秒是状态宽限，不代表任意Python构建都能被强行终止。
真实锁互斥、慢准备下的探活延迟和至少6小时保留边界是上线验收条件。

实施分为：入仓复现→共享读者租约→准备/提交分离→生命周期巡检→一致就绪读取
→回收排他守卫→文档及全模块验证。未来上线期间先暂停公共发布维护，
确认所有API子进程更新并持锁后，再dry-run并恢复维护，避免新旧版本混跑。

本方案没有承诺所有业务路由跨多次字段读取都自动具有事务式版本快照。
原方案时宿主与API只读挂载锁语义尚未验证；后续已通过Linux独立夹具实测，
结果及范围见实施记录，代表性候选负载与生产6小时窗口仍未验收。
内部Planner/Architect/Critic审视由同一代理分别完成，不能代替独立代码复审。
