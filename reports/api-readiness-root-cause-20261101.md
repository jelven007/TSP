# API间歇就绪异常根因调查

日期：2026-11-01。状态：**根因已确认，尚未实施修复**。
本轮调查当前v0.4.39 ECS Full API；机器证据见
脱敏采样与复现清单（附件保存在受控归档）。

根因是**API进程长期绑定旧的不可变公共发布目录，定时保留任务删除该目录后，
健康检查仍沿旧绑定读取清单**。4个API进程中，3个绑定已删除目录，1个绑定有效目录，
请求分配到不同进程，因而交替出现503和200。

## 证据

北京时间2026-11-01 02:47:29–02:49:27，以2秒间隔采样60次：

| 观察 | 实际结果 |
| --- | --- |
| API就绪响应 | 45次503、15次200；本窗口失败比例75% |
| 503失败项 | 45次全部仅为`public_files` |
| 当前公共清单 | 60次均存在、可读取、JSON有效 |
| 请求耗时 | 中位数17.93 ms，最大123.94 ms |
| 数据库、Platform、Compute broker、指标缓存 | 失败响应中均为ok |
| 四类Worker心跳年龄 | 约0.11–5.29秒，均远小于对应120–660秒阈值 |

35秒只读系统调用追踪捕获19次公共清单打开：
17次沿旧目录返回`ENOENT`，2次沿有效目录成功。
按实际API进程汇总，3个进程分别出现6、4、7次失败，另1个进程出现2次成功。
当前公共发布存在，因此不是共享目录整体丢失或当前清单损坏。
这里的35秒是预定采集窗口；追踪命令被窗口限制正常结束，最终确认没有残留追踪进程。

维护日志中精确匹配到该旧目录的删除记录：
北京时间2026-10-31 23:22:02，定时公共发布维护以apply模式删除它，
该次没有研究任务引用保护项。
当时策略保留最新30个发布、当前发布和研究引用，旧发布最小保留时间为6小时。
这次删除比前轮镜像/缓存清理完成时间早约3.08小时；
前轮镜像清理没有删除公共发布目录。

## 调用链

1. API启动以`settings.data_dir.resolve()`建立DataStore，绑定当时的具体发布目录，
   见[Full API生命周期](../backend/app/multitenancy/lifespan.py)。
2. 就绪路由优先使用`app.state.repo.store.data_dir`，
   见[就绪路由](../backend/app/api/routes.py#L77-L98)。
   Full检查在该目录读取`.public_release.json`；缺失即标记`public_files=error`，
   并将市场功能的`ready`置为false，最终返回503，
   见[Full就绪检查](../backend/app/multitenancy/health.py#L96-L128)。
3. PublicQuoteBridge具备检测current变化及切换仓库的能力，但需要调用
   `ensure_fresh()`或更新快照，
   见[刷新与绑定更新](../backend/app/multitenancy/quote_bridge.py#L80-L142)。
   marker流只更新计数及广播，不主动刷新绑定。
4. `/health/ready`不进入业务刷新路径，`/api/health`也在刷新豁免列表；
   部分账户、管理及转发请求同样不会触发刷新，
   见[请求刷新接线](../backend/app/multitenancy/access.py#L38-L66)及
   [按需刷新调用](../backend/app/multitenancy/access.py#L168-L175)。
   因此闲置进程即使持续收到探活，也能无限期停留在旧发布。
5. 保留任务只保护current、最近发布及研究任务引用，未登记API读者仍绑定的发布，
   见[保留候选](../backend/scripts/operations/maintain_full_host.py#L88-L102)及
   [删除执行](../backend/scripts/operations/maintain_full_host.py#L157-L185)。
   旧绑定超过保留条件后被删除，缺失状态首次在这个读者生命周期边界产生。

生产与本地的`health.py`、`quote_bridge.py`、就绪路由文件逐字节哈希一致。
结束核验确认这些生产文件及API主进程身份保持。

## 假设排除及复现

| 假设 | 结论与依据 |
| --- | --- |
| Worker心跳过期 | 本窗口排除：四类心跳均有效，失败项没有Worker |
| 数据库、Compute或Platform依赖超时 | 本窗口排除：检查均为ok，响应耗时不足124 ms |
| 当前清单写入中断、JSON损坏或非原子切换 | 本窗口排除：60次当前清单均有效，系统调用错误指向另一旧目录 |
| API绑定与公共发布保留策略不一致 | 确认：路径追踪、具体维护删除记录、四进程分组和确定性复现相互吻合 |

隔离临时目录中的复现使用真实`release_candidates()`和真实HTTP就绪路由，
数据库与其他依赖使用正常状态替身：

- 旧绑定清单仍存在时HTTP200。
- 正常保留策略删除旧发布、current仍有效后，旧绑定返回503。
- 当前绑定在相同保留操作后仍返回200。
- 仅将失败进程的仓库绑定切换到current，响应即由503恢复200。

期待旧绑定自动恢复的回归断言连续3次失败，均为
`observed HTTP 503, public_files=error`；两个因果对照连续3次通过。
这是已复现的未修复缺陷，不将预期失败写成修复验证通过。
复现脚本和原始追踪日志只保存在工作区外的受控任务目录。

本轮运行现有就绪、心跳、平台桥接和保留模块测试：
`test_function_health.py`、`test_health.py`、`test_multitenancy_worker_process.py`、
`test_full_platform.py`、`test_full_host_maintenance.py`，实际**79项通过**。
现有[闲置桥接刷新测试](../backend/tests/test_full_platform.py#L371-L410)
主动调用`ensure_fresh()`；没有覆盖“健康检查持续到来但没有业务刷新，
旧发布随后被保留任务删除”的跨模块场景。

## 修复方向与验收条件

修复应让每个API进程能够在没有业务请求时同步公共发布绑定。
建议在进程生命周期内执行有界、合并重复请求的发布检查与仓库刷新，
复用现有刷新锁及目录/清单校验；成功切换仓库和相关服务后再报告就绪。
刷新失败继续保留具体失败诊断，不将“current存在”直接等同于旧仓库已恢复。

同时约束保留任务与读者生命周期：仍有活跃读者使用的发布需要保护，
或建立并验证足以覆盖读者切换的回收边界。研究任务的固定输入保护继续保持。
单纯延长保留时间无法解决可无限期闲置的进程；重启API只能临时重新绑定。
本轮没有实施这些措施。

修复验收至少覆盖：

- 多个API进程仅收到探活、无业务请求，发布切换和旧发布回收后仍正确就绪。
- 仓库、行情快照和相关服务绑定保持同一发布，避免混合版本。
- current或清单确实不可用时仍返回503。
- 切换期间正在使用的固定发布及研究输入不会被提前删除。
- 探活延迟保持有界，连续生产观察覆盖原6小时保留边界。
