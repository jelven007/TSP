# `/api/data/status` 超时调查与缓存修复

核对日期：2026-10-28。修复基线为 v0.4.34 /
`18f6f5cbea5bb651dc5fc09f289016bd01b9b6de`。
代码已合入本地工作区，尚未提交、推送或发布到运行服务。

用户反馈为“请求超时（30s）· /api/data/status”。初始认证 HTTP 探测中，本地状态
耗时 26.182 / 13.243 / 10.589 秒；线上为 1.792 / 2.398 / 0.131 秒，均返回 200。
本轮没有稳定复现超过30秒的串行请求。已复现并修复两个会放大扫描负载的并发缺陷，
不把它们表述为所有潜在超时原因都已排除。

## 已确认的缺陷

`api/data.py` 按表缓存统计，日K、增强日K、分钟K包含实际 Parquet 行数和标的数扫描。
`quote_service.py` 更新实时总览缓存，历史采集按表失效数据统计。原
`PublicQueryCache.invalidate()` 每次局部失效都递增全局世代；因此无关的总览或分钟表
更新会丢弃正在计算的日线统计结果。原 `get()` 在锁外扫描，但没有合并同键并发请求，
同时到达的读者会重复执行相同扫描。

新增回归最初连续三轮得到2失败、1通过。扩展用例后临时恢复原实现，得到4失败、
5通过；再恢复修复，回归通过。不同表和数据目录原有的独立读取能力保持通过。

## 修复内容

- 局部失效只改变指定表、命名空间或前缀的世代；全量失效仍清空全部缓存。
- 同一命名空间、数据目录和世代的并发读取共享一次计算；等待和扫描都在锁外。
- 失效后的新请求不等待旧世代，旧扫描不得覆盖新值；成功或异常都会释放等待者。
- 保留既有容量上限、TTL、响应字段和统计口径。前端30秒请求超时未调整。

生产逻辑只修改
[`public_query_cache.py`](../../backend/app/services/public_query_cache.py)。
新增[`并发回归`](../../backend/tests/test_public_query_cache_concurrency.py)，并将

原测试单独执行时，未初始化的全局 `job_store=None` 导致失败，依赖其他测试执行顺序。
没有改变生产任务存储。

## 实际行情基准

使用本地实际 Parquet，日K和增强日K各6,936,704行，分钟K约2,650万至2,708万行。
后台1分钟采集继续写入，两个基准间分钟行数增加，不能将它们称作冻结数据。
测试应用通过实际 FastAPI `/api/data/status` 路由读取只读仓库，任务存储与配置目录
独立。每2秒失效一次总览缓存，模拟无关行情更新；每轮4个并发请求。

| 指标 | 原实现 | 修复实现 |
| --- | --- | --- |
| 并发冷读耗时 | 10.902–10.903秒 | 5.452–5.453秒 |
| 紧接下一轮耗时 | 6.535–7.119秒 | 0.006–0.007秒 |
| 冷读日K / 增强日K / 分钟K计算次数 | 各4次 | 各1次 |
| 下一轮表统计计算 | 增强日K4次、分钟K1次、复权因子4次 | 0次 |
| 每组8个请求 | 全部HTTP 200且小于30秒 | 全部HTTP 200且小于30秒 |

日K与增强日K行数在两组测试中相同。更大分钟数据下，修复后的每张表仍只计算一次。
这是小样本隔离应用基准，不能外推正式P95、生产长期稳定性或线上已部署。
原始结果见 [before](status-benchmark-before.json)、
[after](status-benchmark-after.json)与[复现脚本](benchmark_status.py)。
