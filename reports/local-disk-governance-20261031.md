# 多项目本地磁盘治理建议

盘点日期：2026-10-31。范围为本机数据卷、用户目录、TSP/AIGC/rustdx 项目、Colima、共享缓存和项目临时目录。本次仅执行查询与文件盘点，没有清理目录、停止项目或修改运行配置。

主要治理目标是历史发布、备份、编译产物和数据快照的持续积累。共用容器引擎可以减少重复环境，但仍需分别控制这些目录的保留数量。

## 2. 优先治理的具体对象

### TSP 旧备份与发布缓存：35.48 GiB

- `backups`：18.06 GiB，顶层有 26 个条目，多数为历史备份目录。
- `release-20261028`：9.73 GiB。
- `release-20261028-2`：1.87 GiB。
- `release-20261028-3`：2.15 GiB。
- 其余为分钟数据验证、财务历史、Rust 编译等任务缓存。

已确认旧发布目录包含多份 amd64/arm64 镜像导出 tar、源码包、Git bundle、补丁和验证输出。部分文件记录未提交工作，不能仅凭“cache”目录名判定全部可删除。

处理时先区分：可重新下载的镜像包、可重建产物、唯一的源码或补丁备份、业务数据备份。按同一版本和用途去重。源码恢复集合遵循本项目既有规则：最新版本加最多两个历史版本，合计最多三份；业务数据备份另按恢复要求保留。

### Colima：50.67 GiB

Colima 当前运行 profile 为 `tspp-compute`。Docker/Compose 可用，盘点时没有容器或本地数据卷。

| 项目 | 引擎显示大小 | 引擎标记可回收 |
| --- | ---: | ---: |
| 镜像，48 个 | 52.46 GB | 14.41 GB |
| 构建缓存，439 条 | 13.7 GB | 2.319 GB |

宿主机文件计量：容器数据盘约 49.25 GiB，系统盘约 1.41 GiB。虚拟盘逻辑容量分别为 64 GiB 和 20 GiB。Docker 计量与宿主机文件占用是同一存储的不同视角，不能叠加。

镜像主要是 TSP/TSPP 历史版本，盘点时没有无标签镜像，因此普通 `docker image prune` 不会解决主要占用。当前也没有容器引用镜像，整机 `image prune -a` 会把准备保留的离线运行和回滚镜像一并纳入删除范围。

建议按项目保留当前镜像和最多两个已验证的回滚版本，再删除明确不保留的标签；构建缓存先以 5 GB 为目标容量，按实际重建成本调整。以下是已核对本机 CLI 支持的命令示例，尚未执行：

```bash
export PATH="$HOME/.local/share/tsp-dev/runtime/bin:$PATH"
docker --context colima-tspp-compute system df
docker --context colima-tspp-compute buildx prune \
  --max-used-space 5GB --reserved-space 1GB
```

清理后同时检查引擎内部占用和宿主机 `df`。虚拟机内释放空间不保证宿主机稀疏磁盘文件立即缩小；若未归还，再依据本机 Colima/Lima 支持的回收方式处理，不能直接删除正在使用的磁盘文件。

### Rust 构建与项目临时目录

- `~/.trae-cn/worktrees/rustdx/production-readiness-target`：8.73 GiB，已确认是 Cargo 的 debug、release、doc、package 和跨平台编译输出，没有 `.git`。
- `/private/tmp/rustdx-release-2.0.4-target`：5.01 GiB，同样为 Cargo 编译输出。
- `/private/tmp` 总计 18.32 GiB，另外包含 TSP 部署、策略验证、性能实验与源码副本。
- `/private/tmp/tspp-release-20261030` 约 2.77 GiB，`lsof` 显示仍被 PID 24652 的 Python 进程使用。

先用 Cargo 的指定 target 目录清理入口管理编译产物，后续为每个项目固定一个 target 位置，避免每次任务再生成一套完整编译目录。

临时目录应按任务归档：成果、必要证据和唯一补丁保存后，再回收不再使用的实验数据和依赖。仍在运行或被依赖的目录排除在首轮清理之外。

rustdx 另有两个正式注册的 detached Git worktree，每份约 0.83 GiB；盘点时它们与 main 的 HEAD 相同，且 `git status --porcelain` 均为空。移除前还应确认没有会话继续使用，然后通过 Git 的工作树管理入口处理。

### TSP 运行目录：28.90 GiB

| 子目录 | 占用 | 处理方式 |
| --- | ---: | --- |
| `TSPP/public` | 18.44 GiB | 公开行情数据发布快照，需按引用和保留策略回收 |
| `TSPP/data` | 6.26 GiB | 活跃共享业务数据，按数据集语义管理 |
| `TSPP/releases` | 3.94 GiB | 15 份应用发布副本，按运行和回滚要求保留 |

正在运行的应用副本为 `v0.4.39-bac72d9a83c0`。多数旧副本的 Python `.venv` 是符号链接，并不是 15 套独立 Python 环境；多数副本另有实际的前端依赖目录。

应用副本可以按“正在运行的版本 + 最多两个回滚版本”整理，但应检查注册工作树、引用和唯一修改，不能直接按日期删除。

公开数据快照需要单独治理。盘点时有 516 个发布目录，当前快照清单包含 13,455 个文件。它们是行情数据发布版本，不是前端构建目录。

工作区和正在运行副本的 `backend/app/multitenancy/publication.py` 内容一致。已核对实现：

- 每 300 秒检查并发布；摘要未变化时复用当前版本。
- 未变化文件与上一个不可变快照建立硬链接，变化文件重新复制。
- 成功发布后更新 `current`。
- 本发布模块清除失败的 staging 目录，未见成功历史版本的自动回收。
- Compute 和研究任务通过 `public_release_id` 引用指定历史版本。

因此，长期治理需要为公开数据快照增加或接入按引用回收的机制：保留 `current`、运行及排队任务使用的版本、仍需重放的研究输入和恢复版本；对其余版本按年龄及容量上限回收。不能把源码恢复集合的“三份”规则直接套在业务快照上。

516 个快照之间存在硬链接，逐个测量再相加会重复计算。18.44 GiB 是整个 public 目录一次扫描的结果，也不代表删除旧快照必然释放同等空间。

### TRAE 自身数据与共享包缓存

TRAE 三个互不包含的已确认路径合计约 14.17 GiB：`~/.trae-cn` 11.14、Application Support/Trae CN 1.89、Library/Caches/Trae CN 1.14 GiB。其中 `~/.trae-cn/worktrees/rustdx` 占 10.50 GiB，主要部分为上文的 Rust 编译输出。

TRAE 日志、CKG 索引和聊天快照通过产品入口清理：

1. 打开命令面板，运行 **Help: TRAE Process Explorer**。
2. 进入 **Resources Explorer → Disk**。
3. 选择 **Log Files / CKG Index Storage / Chat Snapshot Files** 的对应清理动作。

不要整体删除 `.trae-cn`、workspaceStorage、扩展或会话历史目录。不要把工作树旁的用户构建输出和产品内部数据混为一类。

Python 缓存已确认由 uv 管理，可先执行 `uv cache prune` 回收不可达对象；需要进一步缩减时，再决定是否清空可重新下载的缓存。依赖目录中的硬链接会影响最终释放量。

## 3. 持续治理规则

| 对象 | 建议规则 |
| --- | --- |
| 容器引擎 | 本机共用一套 Colima；各项目使用独立 Compose 项目名、端口和数据卷 |
| Python / Node 环境 | 每项目独立依赖版本，共用 uv/pnpm 下载缓存 |
| Rust 构建输出 | 每项目固定 target 位置，任务结束后回收临时 target |
| 应用发布与源码恢复 | 当前或最新版本加最多两个已验证历史版本；引用中的版本额外保护 |
| 数据发布快照 | 先按任务、研究重放和恢复引用保护，再按年龄与容量回收 |
| 临时任务目录 | 任务完成后保存成果和必要证据；非活跃目录可采用 7 天回收窗口 |
| 日志与验证输出 | 滚动、压缩、设容量预算；必要审计证据另行归档 |
| 用户数据库和行情历史 | 独立备份与业务保留策略，不按通用缓存规则删除 |

增加 OrbStack 不能自动解决现有历史文件的积累。若后续确有界面管理需求再迁移，并在迁移验收后退出旧环境，避免两套镜像和虚拟盘长期并存。

## 4. 实际执行顺序与验收

1. 先列保留清单：运行进程、镜像版本、注册工作树、唯一补丁、备份和任务引用。
2. 优先处理可重建的 Rust 产物、旧镜像导出包和确认结束的实验目录。
3. 整理 35.48 GiB 的 TSP 旧备份/发布缓存，并为以后任务落实保留数量。
4. 清理 Docker 构建缓存及明确不保留的历史镜像，复核宿主机空间是否归还。
5. 整理旧应用副本，再实现或接入公开数据快照的引用保护和回收机制。
6. 使用 uv、pnpm 和 TRAE 各自的管理入口处理其缓存。

每批执行前后记录 `df`、对应目录 `du` 和 Docker `system df`；确认当前项目页面/API、数据库连接及运行任务仍正常。实际释放空间以执行后的测量为准。

本次交付是盘点结果和治理方案。上述删除、保留策略配置以及公开快照回收代码尚未执行。
