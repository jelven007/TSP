## 2. 实现内容

### 2.1 模拟盘长历史

- 订单、成交、净值接口增加 `limit` 与不透明 keyset cursor，并返回 `total`、`next_cursor`；成交同时返回排除企业行动的 `execution_total`。
- PostgreSQL 直接执行有界分页 SQL；HTTP 历史读取不再调用全量 loader。
- 订单/成交/净值的领域重放仍读取完整台账，分页不改变现金、持仓、费用、T+1、企业行动和修复语义。
- 前端常规查看只取当前页；CSV 导出由用户触发后逐页拉取全量成交。
- schema v6 增加订单历史表达式索引。

### 2.2 研究任务调度

- schema v6 为 `research` 增加 `scheduler.work` 类型和 4 个全机槽位。
- 研究任务插入、状态和租约变化通过触发器更新 due；空租户没有 due 行，不参与 worker 高频扫描。
- `ResearchWorker` 使用 `Scheduler.claim("research")` 有界领取租户，完成后推进下一 due。
- 真实 PostgreSQL 测试覆盖空租户跳过、排队租户全部前进和一次执行。

### 2.3 验收器

新增 `backend/scripts/accept_phase2_step2.py`。脚本自动创建和删除一次性控制库、业务库及最小运行角色，不读取生产数据。

每个用户具有：

- 1 个独立账号、个人租户和 Cookie 会话；
- 20 只自选证券及真实租户写入；
- 240 笔订单、240 笔成交、180 条净值；
- 1 个禁用通知渠道，不发送邮件或 Webhook；
- 1 项研究任务；
- 独立流票据、私有事件订阅和公共行情 marker 订阅。

每轮工作流读取两页订单、成交和净值，并验证 cursor 无重复、总量正确及租户标识未串读。

### 3.2 HTTP 负载

| 负载 | 请求 | 错误 | P95 | P99 | 说明 |
| --- | ---: | ---: | ---: | ---: | --- |
| 100 人同步突发，第 1 轮 | 1,200 | 0 | 1,111.012ms | 1,643.687ms | 所有用户同一步骤同时撞库 |
| 100 人同步突发，第 2 轮 | 1,200 | 0 | 1,457.868ms | 1,662.970ms | 容量饱和证据，不按轻 API 稳态门槛判定 |

同步突发没有 4xx、5xx、超时或传输错误，但明显超过 P95 300ms / P99 1s 建议值。该结果保留为单进程、双 32 连接池的峰值排队证据，不宣称突发延迟达标。错峰稳态满足本地轻 API 建议值。
